# Release Notes — 2026-05-26

## Summary

Two FCs shipped this session, closing out the multi-week text-rendering arc that started with FC-019. **FC-019 spike concluded** by validating an OCR-based text-repair mechanism for Gemini Flash's stochastic narration jumbles — and, critically, by catching that the obvious metric (word-recall) silently passes the dominant failure mode. **FC-020 then productionized** the proven mechanics: narration text is now baked directly into the illustration with a two-axis OCR check (recall + precision), the FC-015/018 Skia overlay is fully deleted, and the production pipeline parallelizes pages against fixed canonical anchors. Adversarial peer review caught a real bug (unbounded character refs) before merge; live integration on an 8-page production story validated the end-to-end quality. The session also surfaced the next-priority latency finding: character-reference generation, not the page pipeline, is now the dominant wall-clock cost.

## Changes

### New Features
- Production stories now render with narration text **baked into the illustration** (not overlaid) — the "true kids' book written + illustrated by an author" feel the user has been pursuing across FC-015/018/019. Sound effects (e.g. "Stomp!", "Peep!") and emphasized words (accent color) are baked too.
- **OCR text-repair**: every generated page is verified via Cloud Vision and regenerated (up to 2 attempts, best-F1 kept) when recall < 0.6 OR precision < 0.75. Catches both missing-text and hallucinated-extra-text failure modes.
- **Cast-lineup reference** (FC-019 → FC-020): a single image showing all characters at correct relative scale is generated once per multi-character story and used as a canonical reference on every page. Persisted as `castReferenceUrl` on the story document.
- **Pin-first-K canonical anchors**: the first 2 rendered pages become fixed references for all later pages. Pages 3..N then generate in **parallel** (bounded concurrency 4) without inter-page dependency — character drift can't propagate, and parallelism is preserved.

### Bug Fixes
- **(spike, FC-019) Recall-only OCR metric silently passed the page-6 jumble.** Root cause: the failure mode is *hallucinated extra gibberish text*, not missing text — every intended word was present, so word-recall scored 1.0. Fixed by adding precision (fraction of OCR-detected words that were intended). Validated deterministically against all 12 historical renders: 11 clean had precision 0.94–1.00; the 1 jumble scored 0.64. Rule: regenerate when `recall < 0.6` OR `precision < 0.75`.
- **(FC-020, review HIGH) Character reference images were unbounded.** A story with many named characters could exceed Gemini's ~14-image multimodal cap on every page and fail the entire book to placeholders. Fixed by `MAX_CHARACTER_REFS = 10`; excess characters still appear in the textual character sheets but only the top 10 (protagonist first) get ref images.
- **(FC-020, review MEDIUM) `isRetryableError` false positives.** Bare `.includes('500')` matched a 429 quota error's "limit ... per 500 seconds"; bare `.includes('INTERNAL')` matched "INTERNAL_ID" in 400s. Both would have triggered retry storms on non-retryable errors. Fixed: anchor 5xx matches to a status/code context, word-bound INTERNAL.
- **(FC-020) Gemini 500 INTERNAL errors weren't retried.** The original predicate only retried 503. A live test dropped a page to placeholder on a transient 500. Fixed by broadening to all transient 5xx + network resets (ECONNRESET/ETIMEDOUT/fetch-failed/socket-hang-up).
- **(FC-020) Stale mobile timeout comment.** `api.ts` said "Cloud Run timeout is 600s" — false (Cloud Run is 3600s per cloudbuild). The 600s ceiling is the *mobile axios client* timeout; if it fires, the server keeps running, finishes, and saves the story, but the user sees an error. Comment corrected.

### Performance & Optimization
- **Production page pipeline is now parallel** (after the K=2 sequential anchor phase) with bounded concurrency 4 — was previously page-1-then-all-rest-with-page-1-as-setting-ref. Reduces page-stage wall-clock and removes a single point of failure.
- **Cast lineup + title page generated in parallel** (both depend only on char refs).
- **Production attempt cap = 2** for OCR text-repair (vs the spike default 3) — bounds the timeout budget while still catching the ~10% stochastic jumble rate.

Tests excluded from production build.

## Key Decisions & Rationale

- **Bake text in image (Gemini Flash) over Skia overlay** — user feedback that the overlay never felt "author-designed." FC-019's spike validated the baked path empirically. The Skia overlay was fully *deleted* (no flag, no fallback) per user direction; rollback granularity is at the PR level.
- **Flash over Pro** — Pro has slightly better text accuracy but **unfixable character drift** (the boy changed 3× in 6 pages). Character consistency is the harder, more product-critical problem; Flash already solves it; text is the narrower fix-able defect. Decision baked into the FC-019 investigation doc; carried forward unchanged in FC-020.
- **Recall + precision (not recall alone, not F1 alone, not gibberish detection)** — the deterministic 12-render sweep showed precision cleanly separates the jumble (0.64) from clean renders (0.94–1.00), with healthy margin on both sides of the 0.75 threshold. Recall alone misses hallucinated-extra-text entirely (the dominant failure). F1 is used internally for *ranking* candidates within the regenerate loop, but the *pass gate* is the two-axis rule because each axis catches a distinct failure mode (recall→missing/garbled, precision→hallucinated/duplicated).
- **Sequential first-K then parallel rest (not all-parallel, not all-sequential)** — all-parallel breaks the canonical-anchor strategy (page N can't reference page 1 if they're racing); all-sequential is correct but throws away the parallelism win. Pin-first-K (K=2) is the smallest sequential head that preserves anchoring while still parallelizing the bulk.
- **Sync now, async later (Option C)** — user picked this over bundling FC-017's async refactor into FC-020. Rationale: ship the proven text quality immediately, keep the migration atomic and reviewable, and pursue the durable timeout fix as its own FC. The 600s mobile ceiling is acceptable for an internal-testing app.
- **Fully delete the Skia overlay (no fallback flag)** — user call. Trade-off: pre-FC-020 stories render with a blank gap where text used to be. Acceptable because the app is internal-testing-only; back-fill is not worth the engineering cost.
- **Stand up Vitest now** rather than defer testing — production behavior change requires tests per the workflow. Extraction to `textVerify.ts` was the right architecture anyway (pure helpers separated from I/O).
- **Spike scaffolding deleted in the same PR** rather than left as dev-only — the spike's purpose was concluded; leaving it as dead code (gated env var + route + secret) would invite drift and clutter the Cloud Run config. One PR = one rollback unit.
- **`MAX_CHARACTER_REFS = 10`** chosen for the cap because Gemini's documented multimodal cap is ~14 images; 10 char + 1 cast + 2 anchors = 13 ≤ 14 with one image of headroom. Protagonist sorted first so the cap drops the least-important characters' refs.
- **Defer FC-017 until prototype works** — user direction this session-end. The sync model FC-020 shipped is acceptable for internal-testing-app prototype validation; FC-017's investigation (why the May-12 instance died: OOM vs network vs scale-down) requires production-scale data we don't have yet.

## Discoveries

- **Character-reference generation, not page generation, is the production wall-clock bottleneck.** Measured on the 8-page Theo story: total 440s, of which the char-ref stage was ~332s (one ref hit a 503 → ~331s end-to-end). The full new page stage (sequential 2 + parallel 6 + OCR + uploads) was only ~62s. This *reframes FC-016* (latency reduction) — the page-parallelization lever FC-016 hypothesized was already implemented by FC-020 incidentally; the remaining latency lever is char refs (caching, downscaling, faster path, fewer refs).
- **Gemini image latency is wildly non-deterministic** — observed 5–15× over spec (per session 2026-04-28 memory) and confirmed again here (one ref took 5.5 min after a transient 503). The sync model's worst case is dominated by this stochastic tail, not by deterministic per-page work.
- **The dominant Flash text failure is HALLUCINATED extra text, not missing text.** Specifically: a second gibberish text block rendered beside the correct one ("Toonallery it, too drenist and ever domr evenuting"). Word-recall scored this 1.00 because every intended word was still present. This is the single most important metric-design lesson from the whole arc — recorded in the FC-019 investigation, the FC-020 plan, and the unit tests so future maintainers won't repeat it.
- **The cast lineup + canonical anchors strategy holds character + setting consistency across the parallel batch** — visually confirmed across cover/p1/p4 of the Theo story (Pixar-3D, boy + dragon).
- **The 600s ceiling is the mobile axios client timeout, NOT Cloud Run.** Cloud Run allows 3600s (pinned in `cloudbuild.yaml`). When the client gives up, the backend keeps running, finishes, and saves the story to Firestore — the user sees an error but the story silently appears on next load. This is a discoverable UX bug to fix in FC-017 (resume/notify model).
- **Cloud Vision needs `roles/serviceusage.serviceUsageConsumer` on the runtime SA** even when the API is enabled, because the project's compute SA has granular roles instead of Editor. Without it, OCR 403s and the (fail-open) scorer returns 1.0 for everything — verification appears to work but does nothing. Watch logs for `[TEXT-VERIFY] OCR failed` to catch this regression.
- **Local Vision scripts need `GOOGLE_CLOUD_QUOTA_PROJECT=ai-storybook-app-2025`** because the user's gcloud ADC quota project is `gen-lang-client-0607444019` (where Vision isn't enabled). Not an issue on Cloud Run.

## Known Issues

- **(MEDIUM, deferred to FC-017) 600s mobile timeout vs char-ref tail latency.** A 12-page story or a single bad char-ref roll could breach the client timeout. When it does, the backend silently finishes and saves the story — confusing UX. Acceptable for the prototype; the durable fix (async/resume) is FC-017, deferred until prototype is working.
- **(MEDIUM, pre-existing) Cloud Run instance can die mid-request and lose ~80% of work** (per the 2026-05-12 incident captured in FC-017). FC-020 didn't change this; FC-017 will, after a root-cause investigation.
- **(LOW, deferred) Title/cover page bakes text but is NOT OCR-verified.** Cover text is short (<60 chars, low jumble risk), so the inconsistency is benign — but a stochastic jumble on the title would ship unchecked. Cheap follow-up.
- **(LOW, pre-existing) `uploadGeneratedImage` failures throw rather than degrading to a placeholder.** A GCS save failure on the sequential phase aborts the whole story; on the parallel phase it 500s the request. Pre-FC-020 behavior; not a regression.
- **(LOW, pre-existing) Duplicate `pageNumber` from Gemini would collapse the results Map.** No dedupe in `generateStory`'s parse path; identical on main pre-FC-020. Unlikely in practice but unguarded.
- **(LOW) Existing pre-FC-020 stories render with a blank gap** where overlay text used to be. Internal-testing app, so back-fill is not worth it — regenerate old stories instead.
- **(LOW) The `>10`-character cap branch is unit-tested + traced but not exercised by a live run.** Typical stories have 2 characters so the cap is a no-op; the rare many-character story would hit the cap path. Cheap follow-up if/when a real such story is generated.
