## Key Decisions & Rationale

- **Drafted both FC-016 and FC-017 plans concurrently rather than sequentially.** They're explicit parallel-not-coupled tracks per both plans' new `Coordination` sections: FC-016 reduces call-level latency, FC-017 buys orchestration-level durability. They touch the same files (`gemini.ts`, `stories.ts`, `textVerify.ts`) but at different sites; no architectural coupling. The Coordination sections name the **one** real ordering nudge — FC-017 Phase 2 (per-phase Firestore writes) before FC-016 Lever A1 (cache lookup), because the cache check slots naturally into the Firestore boundary FC-017 introduces. FC-016's Lever E1 (per-call 60s timeout) is fully independent and can ship any time.
- **One shared Phase 1 instrumentation PR instead of two parallel PRs.** Both plans' Phase 1 wanted overlapping things — structured stage logs, per-call timing, memory snapshots, request-tagged logging. Two near-identical PRs stepping on each other in `gemini.ts` would be friction with no upside. The Coordination sections of both plans pre-committed to the shared-PR approach; this PR is exactly that.
- **Plans treat investigation as Phase 1, not "do it later."** Both FC entries explicitly say investigation must precede architecture work. FC-017 in particular: *"Without knowing whether instances die from OOM vs network vs scaledown, we'd be solving the wrong layer."* The plans gate Phase 2 of each on a written investigation note (`docs/investigations/fc-017-instance-death-${date}.md`, `docs/investigations/fc-016-charref-baseline-${date}.md`). ## Discoveries

- **The 2026-05-12 `TypeError: fetch failed sending request` was already covered by `isRetryableError` in `textVerify.ts`** (line 83: `/fetch failed|socket hang up/i.test(s)`). So the retry harness DOES retry it. What was missing was structured *classification* — the existing code knew "is this retryable: yes" but didn't record "what failure class was this." Phase 1's `classifyError` separates `fetch_failed` from `unavailable` from `internal` from `5xx` so Cloud Logging queries can rank failure-mode prevalence after a real instance death. FC-017 Phase 2's plan for widening `isRetryableError` may turn out to be a no-op once we have the data.
- **`process.memoryUsage()` gives 4 numbers (`rss`, `heapTotal`, `heapUsed`, `external`) and we only emit 3** (`rss`, `heapUsed`, `external`). `heapTotal` was dropped as redundant — `heapUsed` is the more meaningful "growing under load?" signal. Externally-allocated buffers (where the multimodal `imageBase64` payloads live as Node `Buffer` instances) show up under `external`, which is the line most likely to climb during char-ref + page generation and the candidate OOM signal.
- **Cloud Run's behavior on `res.json(...)` is more useful than expected for the future FC-017 Phase 3 work.** A response sent does NOT terminate the JS event loop; the request handler can keep doing work as long as the instance is alive. This is exactly the "silent-success" bug FC-017 calls out today — backend runs to 3600s after the mobile client gives up at 600s. FC-017 Phase 3 plans to *use* that behavior intentionally (202-ACK + background task on the same Cloud Run service) instead of leaking it. The Cloud Run knob that matters is **CPU always allocated** — without it, CPU is throttled between responses and a background task crawls. Verify before relying on this in Phase 3.
- **The FC-017 plan's recommendation against Cloud Tasks / Cloud Functions / a separate worker service is non-obvious but defensible.** The "right" GCP architecture pattern in textbook async-job docs is Cloud Tasks → Cloud Run. For us, today, with ≤ 1 concurrent story per user and full idempotency via the Firestore doc, the queue is overkill. Cloud Tasks becomes the right answer at ≥ 10 concurrent jobs or cross-region failover — not today's volume. Captured the reasoning in the plan so a future session doesn't re-litigate.

## Known Issues

- **(MEDIUM, pre-existing — FC-017 Phase 4 fix) Silent-success on client timeout.** Mobile axios timeout is 600 s; Cloud Run timeout is 3600 s. A 12-page story or a single slow char-ref can push wall-clock past 600 s — the mobile client errors out, but the backend keeps running, finishes the story, and saves it. The user sees a hard error and the story silently appears in the library on next refresh. FC-017 Phase 4 plans to fix this **ahead of the full async refactor** via a mobile `onSnapshot` subscription on the story doc; the fix can ship the moment Phase 2's Firestore per-phase progress writes are live.
- **(MEDIUM, pre-existing — FC-017 root cause) Cloud Run instance can die mid-request and lose ~80% of work.** Observed 2026-05-12. Cause not yet known (OOM vs network vs scaledown). This session's instrumentation is designed to surface the answer — but no run has happened against the new code yet. *Phase 1 next step.*
- **(MEDIUM, pre-existing — FC-016) Char-ref stage dominates wall-clock at ~75% of total.** FC-020's measurement is one data point; Phase 1's baseline sweep is to confirm typicality. The plan's stop-gate explicitly handles the outlier case (≤ 60s p50 / ≤ 120s p95 → downgrade FC).
