### Bug Fixes

- **Duplicate page docs under any double-execution.** Root cause: `worker.ts:387` auto-id'd page-doc references made the success-path `batch.commit` non-idempotent — any race that produced a second successful batch (sweep ↔ stale-lock-takeover; SIGTERM during success batch; bg-catch clobbering a healthy worker; future races we haven't found) wrote a second N-page set; mobile reader rendered every page twice. **Fix:** deterministic page IDs (`storyRef.collection('pages').doc(String(pageNumber))`). Single-line change; closes the entire corruption class as the idempotency floor. (FC-030)
- **Sweep ↔ stale-lock-takeover split-brain.** Root cause: the sweep's bulk `batch.update` would clobber a worker that had taken over (with a fresh heartbeat) between query-prep and the batch landing — setting `status:'failed:orphaned'` + deleting `workerId` while the worker was still running. User's Resume then claimed (no workerId in the way) → two workers on one storyId. **Fix:** sweep now uses per-doc `runTransaction` with a re-read inside the txn; aborts if the predicate no longer holds. (FC-030)
- **SIGTERM during success-path `batch.commit` clobbered `status:'complete'`.** Root cause: the SIGTERM handler did a blind `storyRef.update({status:'failed:sigterm', ...})` that raced the in-flight batch.commit. **Fix:** handler now uses a transaction that refuses to overwrite `complete`/`failed`. (FC-030)
- **`fireWorkerInBackground` catch clobbered a healthy in-flight different-process worker.** Root cause: the catch's re-read-then-update fell through on `status='generating'` and wrote `'failed:unknown'` even when another live worker owned the doc. **Fix:** transactional catch refuses to clobber when `workerId !== WORKER_ID`. **But** preserves own-process recovery (the `!== WORKER_ID` distinction — without it, the user is stranded for ~10 min when this process's own catch fails to write the terminal marker). (FC-030)
- **`/generating` screen stranded the user on completed stories after Resume.** Root cause: `navigatedRef.current` was a plain boolean reset only on `useEffect` remount (id change); after a Resume cycle that flowed `generating → failed → Resume → complete` on the same screen instance, the boolean stayed `true` from the first (aborted) nav attempt → the `'complete'` snapshot never triggered `router.replace` → user saw "Starting…" forever on a completed story. **Fix:** ref now keyed on `(id, attempt)` — a new attempt re-enables nav. (FC-031)
- **Silent-queued window.** Root cause: the route's initial `set()` didn't populate `progress`, so the first snapshot mobile received had `progress=undefined`; a hard worker death (no SIGTERM) was indistinguishable from normal startup for up to 5–15 min until the sweep noticed. **Fix:** route now populates `progress.phase='queued'` + `progress.message='Starting…'` + `progress.updatedAt=serverTimestamp()` synchronously. Required adding `'queued'` to `GenerationPhase`. (FC-031)
- **Reintroduced FC-025 B-4 nested-`serverTimestamp` footgun.** Caught during FC-031 adversarial review: my initial-progress populate had `updatedAt: FieldValue.serverTimestamp()` inside a map literal — exactly the pattern FC-025 B-4 ruled forbidden (silently serializes as null on some SDK versions). **Fix:** split into `set()` (no sentinel) + dot-notation `update({'progress.updatedAt': ...})`. (FC-031 fix commit)
- **iOS EAS build failed with `npm ci can only install when package.json and package-lock.json are in sync`.** Root cause: `@firebase/auth` declares `@react-native-async-storage/async-storage@^1.18.1` as an optional peer; the project pins async-storage 2.2.0. npm 11 (local, Node 24) dedupes and omits a 1.x copy; npm 10 (EAS builder, Node 20) rejects the resulting lockfile. **Fix:** regenerated `mobile/package-lock.json` with npm 10 (`npm@10 install --package-lock-only`). Verified `npm ci --include=dev` passes under both 10 and 11 (1037 packages). The nested 1.x copy is unused at runtime — app code resolves the hoisted 2.2.0. (PR #39, separate session)

## Key Decisions & Rationale

- **Deterministic page IDs as the load-bearing fix vs. only narrowing race windows.** The three race-narrowing changes (sweep tx, SIGTERM tx, bg-catch tx) reduce double-execution windows but none *prove* elimination. Deterministic IDs guarantee that even if a race fires, the resulting writes are idempotent — same doc IDs, identical content, last-write-wins is benign. Closes the corruption class for races we haven't found yet too. The cleanup tax (legacy auto-id'd page docs for completed stories) is zero because the reader queries by `.orderBy('pageNumber')`, not by doc ID. One-line change with the highest leverage in the entire retrospective remediation. (Vs. only doing the race-narrowing: leaves the corruption class open to any future race we discover.)

- **Sub-FC pattern (FC-030/031/032) for retrospective remediation, not "amend FC-017".** Each got its own plan + PR + adversarial review for clean rollback granularity and orthogonal review scope (correctness reviewer vs. mobile reviewer vs. ops reviewer). Same pattern as FC-025 worked well for PR #26. (Vs. one big remediation PR: would have produced a sprawling review with mixed concerns and ambiguous rollback boundaries.)

- **OIDC migration for sweep auth deferred** (filed as future FC, not yet planned). FC-032 plan §6 originally framed it as PRs 2+3 of the same FC. Given context budget + rotation closing the immediate concern + the gap noted in `recreate-alerting.md` for future re-deploy, deferring was the right call. (Vs. doing it now: 3 sequenced PRs, accept-both → cutover → cleanup; not feasible inside this session.)

- **Skipped the `ASYNC_JOBS_ENABLED` feature flag from the original FC-017 plan.** Two-round adversarial review concluded the flag added complexity without de-risking — the 202-ACK path is strictly safer than the sync path (no client-timeout failure mode), and Phase 2's progress writes mean the silent-success fix already works for the sync path. Rollback is the same in either case (revert the PR). (Original plan recommended the flag; the adversarial review's clearer-eyed assessment justified the deviation.)

- **In-memory Firestore double for FC-030 tests, not a full emulator.** The emulator setup is ~1 day of test infra; the in-memory double covers the predicates' logic in ~30 LOC. Real concurrency proof deferred to FC-033 (filed). (Vs. skipping tests entirely: the predicates have non-obvious race semantics that need regression coverage; vs. emulator: not worth the setup cost for this PR.)

- **Use `'queued'` as the honest pre-claim `GenerationPhase` value, not `'story-text'`.** The initial-progress populate runs before the worker has claimed the lock. Writing `phase: 'story-text'` would be a lie — misleading for any downstream consumer (analytics, debug dashboard) that reads `phase` directly. Added `'queued'` to the type union; worker overwrites with `'story-text'` on its first `saveProgress` after claim. (Vs. lying: the test code is now exhaustive on the enum and the lie would propagate.)

- **System-level retrospective review as a new pattern.** The per-PR adversarial review pattern (even at the two-round + confirmation tier used for PR #29) is structurally blind to system-level interactions. The 2026-06-23 retro with 4 parallel reviewers (each a distinct domain lens) caught BLOCKERs all three prior PR reviews missed. Worth codifying in CLAUDE.md for future FCs of this scale (multi-phase, distributed, multi-process). The cost is ~4 parallel agents × ~30–60 sec each; the value is catching a bug class per-PR review can't.

## Discoveries

- **`gcloud firestore` has no `documents` subcommand.** It exposes only `backups | databases | fields | indexes | locations | operations | user-creds` groups and `bulk-delete | export | import` verbs. My first runbook draft used `gcloud firestore documents read` / `update` — caught by FC-032 adversarial review as BLOCKER-1. Use Firebase Console URLs or a Node one-liner with `@google-cloud/firestore` Admin SDK (e.g. `new Firestore().doc('stories/STORY_ID').get()`) instead. Runbooks now reflect this.

- **`FieldValue.serverTimestamp()` nested inside a map literal may silently serialize as null** on some `@google-cloud/firestore` SDK versions. This is the FC-025 B-4 footgun. I reintroduced it in FC-031's initial-progress populate; adversarial review caught it. **Rule:** sentinels go top-level on `set()`/`update()`, or via dot-notation (`'progress.updatedAt': FieldValue.serverTimestamp()`). Always `grep FieldValue.serverTimestamp` after adding any new write site. The current SDK (v7.11.6) handles nested sentinels correctly, but the failure mode is silent and a future downgrade re-exposes it.

- **`npm ci` lockfile compatibility differs across npm major versions.** npm 11 (Node 24, local) dedupes optional peer-dep copies; npm 10 (Node 20, EAS builder) rejects the resulting lockfile. `@firebase/auth` + a pinned `async-storage 2.2.0` was the specific trigger (firebase wants 1.x peer; npm 11 dedupes the 1.x copy out; npm 10 wants to see it nested). Lockfiles regenerated under npm 10 work on both. **Rule:** regenerate `package-lock.json` with the EAS builder's npm major (currently npm 10) so `npm ci` is portable.

- **Newly-created Cloud Logging log-based metrics take ~1–10 min to become queryable.** Until they propagate, `gcloud monitoring policies create` referencing them fails with `Cannot find metric(s) that match type = "logging.googleapis.com/user/<name>"`. The `recreate-alerting.md` runbook now documents the polling recipe: `until gcloud monitoring policies create --policy-from-file=… 2>&1 | grep -qE "^Created|already exists"; do sleep 30; done`.

- **Cloud Run secrets referenced via `:latest` are resolved at container start, NOT live.** Rotating a secret (new version) does NOT propagate to a running revision; you must roll a new revision (`gcloud run services update --update-secrets=…`) to force re-resolution. Combined with the Scheduler header storing the literal token value, rotation is a 4-step order-sensitive ritual now codified in `docs/runbooks/secret-rotation.md` (with Scheduler pause/resume bracketing to avoid alert-noise during the cutover).

- **The sweep ↔ stale-lock-takeover race window is ~100–500ms** (not 30s, as the retrospective reviewer initially described). Within-region Firestore queries are strongly consistent for committed writes; the race window is bounded by the sweep's query `.get()` → `batch.commit()` latency, NOT by index propagation. Still a real BLOCKER (a worker takeover landing in that window gets clobbered), but the exposition matters when reasoning about future race windows.

- **Cloud Scheduler bearer-token values are readable via `gcloud scheduler jobs describe`** to anyone with `roles/cloudscheduler.viewer` (granted by `roles/viewer` aka Project Viewer). Static-bearer tokens for Cloud-internal traffic have been a Google anti-pattern for >5 years. OIDC closes this; deferred to a future FC.

- **Cloud Run rollback's `update-traffic` shift is INSTANT, but with `--min-instances=0` the prior revision has scaled to zero** → the first request takes a 5–15s cold start. Pre-warm with 2–3 curl hits before declaring rollback successful (now documented in `cloud-run-rollback.md`).
