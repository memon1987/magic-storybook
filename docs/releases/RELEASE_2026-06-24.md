## Changes

### Correctness (FC-030 — PR #34, `cf4c362`)

Four defense-in-depth changes closing the duplicate-pages-in-subcollection corruption class:

- **Deterministic page-doc IDs** — `worker.ts:387` now writes `pages/1`, `pages/2`, … instead of auto-id'd refs. Two successful batches in different lifetimes write the same doc IDs with identical content; last-write-wins is benign. **This is the load-bearing idempotency floor** — closes the corruption class under ANY double-execution path (sweep ↔ takeover race, SIGTERM during success-batch, bg-catch clobbering, future races we haven't found).
- **Sweep transactional re-read** — `admin.ts` now uses per-doc `runTransaction` with `.limit(100)` per query. Re-validates the stale-heartbeat predicate inside the tx so a takeover that landed a fresh heartbeat between query-prep and batch-commit is preserved. Surfaces `failedIds` + uses error-level logging so per-doc tx failures are discoverable.
- **SIGTERM-aware finalize** — handler now uses a transaction that refuses to overwrite `status:'complete'` or `status:'failed'`. Closes the race where SIGTERM during the ~100-500ms success-path `batch.commit` window clobbered status to `'failed:sigterm'`.
- **`fireWorkerInBackground` transactional catch** — refuses to clobber a terminal status OR a `generating` status owned by a *different* process's `WORKER_ID`. Critically, it RECOVERS when status is `generating` with this process's own `WORKER_ID` — meaning the worker's own catch failed to write the terminal marker (transient Firestore blip). Without the `workerId !== WORKER_ID` distinction, the user would be stranded for up to 10 min until the orphan sweep noticed.

All three transactional predicates exported as pure-ish functions; tests exercise production code directly. Backend suite 51→68 tests.

### Mobile UX (FC-031 — PR #36, `47e6b00`)

Four changes closing the user-visible residuals R2 + R4 surfaced:

- **Library `refetchInterval: 15s`** while any row is `queued`/`generating`; stops when all rows terminal. Without this, React Native has no window-focus signal so the library was stuck showing "Generating page 3 of 6" forever after the story completed — directly contradicting the FC-017 plan's "feel free to come back later — we'll have it ready in your library" promise.
- **`navigatedRef` now keyed on `(id, attempt)`** instead of a plain boolean. After a Resume cycle (`generating → failed → Resume → complete` on the same screen), the boolean stayed `true` from the first (aborted) nav attempt and the user was stranded on /generating with "Starting…" forever on a completed story.
- **Initial-progress populate** in the backend route's `set()`. The very first snapshot mobile receives now has `progress.phase='queued'` + `progress.message='Starting…'` + `progress.updatedAt=serverTimestamp()` instead of `progress=undefined`. Eliminates the silent-queued window where a hard worker death looks identical to normal startup. Required adding `'queued'` to the `GenerationPhase` type union.
- **Retry budget + safety-blocked UX**. `attempt` added to the `CLIENT_VISIBLE_DOC_FIELDS` allowlist; mobile failure branch caps Resume at 3 attempts AND suppresses Resume entirely for `safety_blocked` (replaying the same prompt always fails the same way). Replaces with "Create a new story" CTA. Closes the cost-loop where a determined user could burn ~$0.50-$1.10/Resume in a tight retry loop.

Mobile changes ship on the next EAS build (not done yet — tracked separately).

## Key decisions

- **Deterministic page IDs as the load-bearing fix.** The three race-narrowing changes (sweep tx, SIGTERM tx, bg-catch tx) all reduce the window for double-execution, but none can be PROVEN to eliminate it. Deterministic IDs guarantee that even if a race somehow fires, the resulting writes are idempotent. The cleanup tax (legacy auto-id'd page docs for completed stories) is zero because the reader queries by `.orderBy('pageNumber')`, not by doc ID. One-line change with the highest leverage in the entire retrospective remediation.

- **Sub-FC pattern (FC-030/031/032) for retrospective remediation.** Same pattern as FC-025 (PR #26 post-merge adversarial review). Keeps the parent FC plan readable while still recording remediation in the FC index. Used again here for the three orthogonal classes (correctness / UX / ops) — each got its own plan + PR + adversarial review for clean rollback granularity.

- **OIDC migration for sweep auth deferred.** FC-032 plan §6 originally framed it as PRs 2+3 of the same FC; given context budget + the rotation already closing the immediate concern, deferred to a separate FC. Recipe documented in `recreate-alerting.md` for when it lands.

- **System-level retrospective review as a new pattern.** The per-PR adversarial review pattern (even at the two-round + confirmation tier used for PR #29) is structurally blind to system-level interactions. The 2026-06-23 retro caught BLOCKERs all three prior reviews missed. Worth codifying in CLAUDE.md for future FCs of this scale.
