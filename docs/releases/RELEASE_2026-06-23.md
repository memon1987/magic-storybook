# Release Notes — 2026-06-23

## Summary

**Closed out FC-017 (Story generation reliability — request resumes / async job model)** by shipping Phase 3 (async 202-ACK + background worker) and Phase 4 (mobile live-progress screen + orphan sweep) in [PR #29](https://github.com/memon1987/ai-storybook-app/pull/29), squash-merged as `fc8944a`. The 3-5 min synchronous `POST /api/stories/generate` is gone: the mobile client now gets a 202 in ~100-500ms with `{ storyId, status, location, statusUrl }`, navigates to a dedicated `/story/[id]/generating` screen, and watches the Firestore doc update through char-ref → title → pages → save. A 10-min Cloud Scheduler sweep marks any orphaned generating/queued stories `failed:'orphaned'` so a dead Cloud Run instance no longer leaves a story stuck-spinning forever. **FC-017 is Done end-to-end** (Phase 1 instrumentation in PR #23, Phase 2 resumability + FC-025 remediation in PR #26, Phase 3+4 in PR #29). ## Changes

### New Features
- **`POST /api/stories/generate` now returns 202** with `{ storyId, status:'queued', location, statusUrl }` instead of awaiting the full ~3-5 min worker run. The Firestore doc is the source-of-truth for completion.
- **`POST /api/stories/:id/resume`** — re-runs the worker against the same Firestore doc. Phase 2's per-phase checkpoints (`completedPageUrls`, `castAttempted`, `titleAttempted`) mean a resumed run only re-does what's missing.
- **Mobile `/story/[id]/generating` screen** — subscribes to `stories/{id}` via `onSnapshot`, renders `progress.message` and a determinate bar from `completedSteps / totalSteps`, surfaces FAILURE_COPY for each `FailureCode` with a Resume button on terminal failure. useRef-guarded auto-navigation to `/read` on `status==='complete'` so an `onSnapshot` re-fire after navigation doesn't double-route.
- **Library renders queued/generating/failed rows** with status chips. Tapping a non-complete row opens `/generating`; tapping a complete row opens `/read`.
- **`POST /api/admin/sweep-orphans`** — bearer-auth'd admin endpoint that finds stories with `status='generating'` AND stale `workerHeartbeatAt`, OR `status='queued'` AND stale `createdAt`, both older than 5 min, and marks each `status:'failed'`, `failureReason:'orphaned'`. Wired to a `*/10 * * * *` Cloud Scheduler job.

### Bug Fixes
- **Silent-success bug** — backend kept running to its 3600s Cloud Run timeout past the mobile's 600s axios timeout, finished, and saved the story; user saw a generic error but the story silently appeared later. **Fix:** Firestore-driven completion. The mobile client never waits on the request; it waits on the doc.
- **Instance-death data loss** — a dying Cloud Run instance mid-generation orphaned the request; the new instance didn't pick it up. **Fix:** the orphan sweep marks the doc failed within 5 min, surfacing a Resume button. Phase 2's resume cheaply re-runs only the missing phase(s).
- **DELETE 409 guard** — `DELETE /api/stories/:id` now refuses to remove a story while `status` is `queued` or `generating` (would orphan the worker's writes).
- **`pickClientFields` schema leak** (caught by PR #29 Round 2 adversarial review) — the previous `...storyData` spread leaked `workerId`, `workerHeartbeatAt`, `storyText`, `pageUrls`, `attempt`, `castAttempted`, `titleAttempted` to the client. **Fix:** allowlist via `CLIENT_VISIBLE_DOC_FIELDS`, regression test in `backend/src/routes/__tests__/clientFields.test.ts`.

### Performance & Optimization
- **`cloudbuild.yaml`** pinned to `--no-cpu-throttling --timeout=3600 --memory=2048Mi --concurrency=4`. CPU-always-allocated is the non-negotiable prereq for the fire-and-forget worker to keep running after the 202 response ships.

### Infrastructure
- **Cloud Run revision `storybook-api-00123-h75`** — first revision with `SWEEP_AUTH_TOKEN` bound (from Secret Manager `sweep-auth-token:latest`).
- **`firebase deploy --only firestore:indexes`** — pushed three new composite indexes (`userId+createdAt DESC` for `getStories`; `status+workerHeartbeatAt ASC` for the generating-orphan sweep; `status+createdAt ASC` for the queued-orphan sweep) while preserving the legacy `status+userId+createdAt` index by adding it back to `firestore.indexes.json` (firebase deploy is additive but the file is the source of truth — leaving the legacy index out of the file risked it being garbage-collected in a future deploy).
- **`firebase deploy --only firestore:rules`** — pushed owner-read-only on `stories/{storyId}` and the `pages` subcollection; all client writes denied. The mobile `onSnapshot` subscription on `/generating` depends on this rule existing in production.
- **Cloud Scheduler job `sweep-orphans`** — `*/10 * * * *` UTC, bearer-token in `Authorization` header, POST `{}` body. First manual trigger returned `FAILED_PRECONDITION: index is currently building` (expected — the composite indexes need ~1-10 min to build); scheduler retries cover this.
- **Constant-time auth** on the sweep endpoint via `crypto.timingSafeEqual` (vs. JS `===` which is variable-time and can leak the token character-by-character under a sufficiently sensitive timing oracle). 401 on missing or wrong token, 503 if the env var isn't set (fail-closed).

## Key Decisions & Rationale

- **Skipped the `ASYNC_JOBS_ENABLED` feature flag.** The plan recommended a flag for the first 24h canary. The two-round adversarial review concluded the flag added complexity without de-risking — the 202-ACK path is *strictly safer* than the synchronous flow (it eliminates the client-timeout failure mode entirely), and Phase 2's progress writes mean the silent-success fix already worked for the sync path. Rollback is the same in either case: revert the PR.
- **No push notification when a story finishes (deferred).** Plan called out passive in-app surface (library row updates via `onSnapshot`) as sufficient for this round. Push notifications are a follow-up if abandonment metrics show the in-app signal isn't enough.
- **Stayed on the existing Cloud Run service for the worker** (no separate worker service, no Cloud Tasks). `--no-cpu-throttling` makes the in-process fire-and-forget pattern reliable enough for the current load profile and removes one whole class of deploy complexity. If load or failure-rate metrics shift, a separate worker service is the documented contingency in the plan.
- **5-min orphan threshold vs. the worker's 90s stale-lock threshold.** The sweep deliberately runs well above the lock-takeover window so it doesn't fight an in-flight take-over attempt. A worker that's actively retrying is not orphaned; a worker that's been dead for >5 min with no heartbeat clearly is.
- **`pickClientFields` as an allowlist, not a blocklist.** The Phase 2 doc schema added 7 internal fields and might add more. A blocklist must be updated every time the schema grows; an allowlist fails closed when someone forgets.
