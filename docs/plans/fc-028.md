## Context

The reader is landscape-locked and (since FC-026) renders pages with `fit="contain"` + a blurred ambient backdrop. Images letterbox by exactly the gap between the generated aspect ratio and the device ratio; Gemini currently picks its own ratio per image. Pinning a 16:9 landscape ratio on all backend image-generation calls shrinks those letterbox bands for **new** stories. Existing stories are unaffected (baked images are frozen) and already covered by the mobile contain/backdrop — this is polish, not a fix. See the FC-028 entry and FC-026's plan for the motivating clipping/letterboxing history.

**SDK finding (verified 2026-07-05):** the installed `@google/genai` is **v0.7.0**. In `backend/node_modules/@google/genai/dist/genai.d.ts`, `GenerateContentConfig` (line ~1104) has **no `imageConfig` and no `aspectRatio` field** — `aspectRatio?: string` exists only on `GenerateImagesConfig` (the Imagen `generateImages` API, line ~1430) and `GenerateVideosConfig` (line ~1511), neither of which this app uses. So as of today the config-level pin is **not expressible** through the installed SDK, and Path B below is the expected outcome. The executor must still re-run the check at execution time (step 1) — main may have upgraded the SDK by then (newer `@google/genai` releases added `imageConfig.aspectRatio` to `generateContent`).

## Goals

- All four image-generation call sites in `backend/src/services/gemini.ts` request 16:9 landscape output via **one shared constant** (`IMAGE_ASPECT_RATIO = '16:9'`).
- Uniformity across char refs, cast lineup, title page, and story pages — consistency of char-ref inputs vs page outputs matters for the multi-reference pipeline.
- Vitest coverage asserting every image call site carries the pin (config or prompt, per the path that lands). No real API calls.

## Non-goals

- No mobile changes (FC-026 contain/backdrop already handles ratio mismatch; existing stories stay as-is).
- No `@google/genai` version upgrade in this FC (a dependency bump is its own risk surface; if Path B lands, file a follow-up FC for the upgrade + config-level pin).
- No changes to the OCR text-verify thresholds, retry logic, or worker orchestration (`worker.ts` only calls `generateStory`/`generateAllIllustrations`; it never touches generation config).

## Proposed approach

### Step 1 (mandatory first step): SDK-surface check

In the worktree, inspect `backend/node_modules/@google/genai/dist/genai.d.ts` (the `typings` entry of the installed package): does `GenerateContentConfig` contain `imageConfig` (or any aspect-ratio field usable with `responseModalities: ['IMAGE']`)? `npx tsc --noEmit` is the enforcement: a config key not in the type fails compile. Record the finding (SDK version + field present/absent) in the PR description. If present, verify `'16:9'` is an allowed value (check the `ImageConfig` type / its doc comment); if the allowed set differs, use the closest landscape value and record the substitution.

### Path A — SDK supports config-level pin

1. Add near the model constants in `gemini.ts` (~line 90): `const IMAGE_ASPECT_RATIO = '16:9';` with a comment referencing this plan.
2. Add `imageConfig: { aspectRatio: IMAGE_ASPECT_RATIO }` to the `config` object of all four `ai.models.generateContent` image calls in `gemini.ts`:
   - `generateIllustration` → inner `generateOnce` (~line 410)
   - `generateCharacterReference` (~line 527)
   - `generateCastReference` (~line 611)
   - `generateTitlePage` (~line 696)
3. Tests (`backend/src/services/__tests__/gemini-aspect.test.ts`): `vi.mock('@google/genai')` with a **capturing** mock — record the `config` argument of every `generateContent` call (copy the mock scaffolding from `resume.test.ts`, which already mocks `@google/genai`, `@google-cloud/storage`, and `@google-cloud/vision` and imports after `vi.mock`). Invoke each of the four exported functions directly (`generateIllustration` with `opts: { verifyText: false }` to skip OCR; `generateCharacterReference`; `generateCastReference`; `generateTitlePage`) and assert every captured config has `imageConfig.aspectRatio === '16:9'` and `responseModalities: ['IMAGE']` still present.

### Path B — SDK does not support it (STOP-CONDITION fallback, expected with v0.7.0)

1. Do NOT add unsupported config keys. Document the finding (exact SDK version, type-def evidence) in the PR description and in this plan's Execution notes; mark the change **best-effort prompt-level**.
2. Add to `backend/src/prompts/` a single shared constant, e.g. `export const ASPECT_RATIO_INSTRUCTION = 'Compose the image in landscape 16:9 aspect ratio (wider than tall).';` (new tiny module `backend/src/prompts/aspect.ts`, or exported from `illustration.ts` — executor picks the smaller diff), and append it to the output of all four prompt builders: `buildIllustrationPrompt`, `buildTitlePagePrompt`, `buildCharacterReferencePrompt`, `buildCastReferencePrompt`. Note: `illustration.ts` and `titlePage.ts` already say "Landscape orientation (wider than tall)" — the shared line strengthens this to an explicit 16:9 and, critically, extends it to the char-ref/cast prompts which currently specify no orientation at all.
3. Tests: same capturing-mock structure, but assert the **prompt text** sent to `generateContent` (the `contents` argument's final text part for `generateIllustration`/`generateTitlePage`, the sole text part for char/cast refs) contains the shared instruction, for all four call sites. Plus a unit test that each of the four prompt builders' output contains `ASPECT_RATIO_INSTRUCTION`.
4. File a follow-up FC entry: "Upgrade @google/genai and convert FC-028 prompt-level ratio to config-level `imageConfig.aspectRatio`."

Either path: one shared constant, four call sites, no other behavior change.

## Risks & mitigations

- **Silently-ignored config (Path A):** the model/API may accept `imageConfig` but ignore it for this model. Mitigation: owner's post-merge real-generation check measures actual output dimensions; if ignored, fall back to Path B in a follow-up commit.
- **Ratio change regresses baked-text accuracy (FC-020 OCR pipeline):** a wider frame changes text layout. Mitigation: the OCR verify-and-regenerate loop already gates every page (recall/precision thresholds unchanged); owner's post-merge check explicitly confirms text-repair still passes.
- **16:9 char-ref model sheets look odd (white-bg sheets were ratio-free):** accepted per the pre-made uniformity decision — consistent ref geometry beats per-stage ratios for the multi-reference pipeline.
- **Prompt-level pin is best-effort (Path B):** the model may not honor it exactly. Accepted and documented; config-level pin arrives with the SDK-upgrade follow-up FC.

**Path taken:** **Path B (prompt-level, best-effort)** — the STOP-CONDITION fallback, as the plan predicted for v0.7.0.

**Step-1 SDK finding (verified in the worktree at execution time):**
- Installed `@google/genai` = **v0.7.0** (`node_modules/@google/genai/package.json`; `typings: dist/genai.d.ts`).
- `GenerateContentConfig` (`dist/genai.d.ts:1104`) field list ends at `thinkingConfig` — it contains **no `imageConfig` and no `aspectRatio`** field. There is **no `ImageConfig` interface** anywhere in the type defs.
- The only `aspectRatio?: string` fields are on `GenerateImagesConfig` (`:1430`, the Imagen `generateImages` API) and `GenerateVideosConfig` (`:1511`) — neither used by this app (it calls `generateContent` with `responseModalities: ['IMAGE']`).
- Therefore a config-level `imageConfig.aspectRatio` pin is **not expressible** through the installed SDK and would fail `tsc`. Confirmed empirically: `npx tsc --noEmit` stays clean with the prompt-level change (Path B), and would have failed on a config key not in the type.

**What changed (final, post-review):**
- New shared constant `backend/src/prompts/aspect.ts` → `ASPECT_RATIO_INSTRUCTION` = `"Aspect ratio: 16:9 landscape (wider than tall), without shrinking the bottom text band."`.
- Placed it **inside the COMPOSITION block** (next to the existing "Landscape orientation" line), NOT as the final line, of the two USER-VISIBLE builders only:
  - `buildIllustrationPrompt` (`illustration.ts`) — both the has-text and no-text COMPOSITION branches.
  - `buildTitlePagePrompt` (`titlePage.ts`) — inside its COMPOSITION block.
- New test `backend/src/services/__tests__/gemini-aspect.test.ts` (capturing mock over `@google/genai`, mirroring `resume.test.ts`): asserts the **page + title** call sites (`generateIllustration`, `generateTitlePage`) CARRY the instruction in `contents` and still request `responseModalities: ['IMAGE']`, AND asserts the **char-ref + cast** call sites (`generateCharacterReference`, `generateCastReference`) do NOT — so the scope narrowing is pinned by the test in both directions. Plus five builder-level unit tests. 9 tests.

**Deviations from plan (2 — both driven by the two-reviewer gate):**
1. **Scope narrowed from "all four sites uniformly" → page + title only.** The plan pre-decided uniformity across all four builders (Execution contract; Risks #3 accepted 16:9 char-ref sheets). Reviewer 2 (gen-AI image-pipeline persona) returned REQUEST_CHANGES: the char-ref (single 3-pose sheet) and cast-lineup sheets are **internal white-background model sheets never shown to the user**, so the letterboxing motivation — the entire point of FC-028 — does not apply to them; pinning them is pure downside on the consistency-critical multi-reference pipeline (can only shrink the reference figures that anchor every page). The pin was therefore **dropped** from `buildCharacterReferencePrompt` + `buildCastReferencePrompt`, restoring their pre-FC-028 (ratio-free) status quo. This supersedes the plan's uniformity pre-decision; recorded here as the required paper trail.
2. **Constant is a dedicated tiny module** (`aspect.ts`) rather than an export from `illustration.ts`, to avoid any import-cycle question across the prompt files and keep the diff self-evident (plan explicitly left this to the executor).
- Wording/placement also adjusted per review: dropped the unbounded intensifier "noticeably" and subordinated the ratio to the baked-text band; moved out of the recency-privileged final slot into COMPOSITION so the text-accuracy constraints keep the last word.

**Follow-up filed:** FC-042 (`docs/FUTURE_CONSIDERATIONS.md`) — "Upgrade @google/genai and convert FC-028 prompt-level ratio to config-level `imageConfig.aspectRatio`."

**Quantified post-deploy guardrail (replaces the plan's one-story check; Reviewer 2 HIGH):** a single story is not a control for a ~10% stochastic baked-text failure. After the owner-triggered Cloud Run deploy, over the first **≥5** real stories, log/read the FC-020 text-verify **pass rate** and **regeneration count** per page from Cloud Logging and compare against the pre-deploy baseline. **Revert trigger:** text-verify pass-rate drop **> 5 percentage points** OR per-page regeneration rate materially up vs baseline → revert the one commit and route the ratio pin to the config-level FC-042 instead. This is the load-bearing safety control for the change and is copied into the PR body's post-merge checklist.
