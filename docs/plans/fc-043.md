## Context

> **Corrected 2026-07-08 (see Execution):** the original premise below — "zero triggers, nothing auto-deploys" — was **wrong**, caused by querying the *global* Cloud Build region instead of `us-central1`. A regional trigger `deploy-storybook-api` has auto-deployed every push to `main` since 2026-04-04. FC-043's real, still-valuable change became **adding path filtering** to that existing trigger (it fired on every push — mobile/docs included — causing wasted deploys and a concurrent-deploy failure). The corrected record is in the Execution section; the original problem statement is kept below for provenance.

The backend has a deploy pipeline `cloudbuild.yaml` (repo root): `npm ci` → `npm test` (FC-032 test gate) → docker build → push to Artifact Registry → `gcloud run deploy storybook-api` with pinned `--timeout=3600`, `--memory=2048Mi`, `--max-instances`, `--no-cpu-throttling`. A 2nd-gen GitHub↔GCP connection `github-connection` (region `us-central1`) links `memon1987/ai-storybook-app`.

~~**`gcloud builds triggers list` returns zero triggers. Nothing invokes `cloudbuild.yaml` on push.**~~ *(Wrong — was a global-vs-regional query error; the trigger existed and was firing. See Execution.)*

The actual gap worth fixing: the existing trigger had **no path filter**, so every push to `main` (including mobile-only and docs-only commits) triggered a full backend rebuild+deploy — wasteful, and it produced a concurrent-deploy failure when several merges landed at once.

## Goals

- A merge to `main` that changes backend code automatically runs the `cloudbuild.yaml` test→build→deploy pipeline, so `main` and the live Cloud Run revision stay in sync.
- Backend changes only: docs-only or mobile-only merges must NOT trigger a backend rebuild/redeploy.
- Bootstrap: deploy the current `main` (which carries the unshipped FC-037/041/028/016 backlog) as part of enabling this, and use that run to validate the pipeline end-to-end.

## Non-goals

- **Staging environment / manual-approval gate** — deferred to FC-009. This ships auto-deploy-straight-to-prod, accepted for the current pre-launch/low-user stage. Rollback is the Cloud Run revision-rollback runbook (FC-032 `docs/runbooks/`).
- **Mobile/EAS CD** — EAS builds stay owner-triggered (no OTA; App Store submission needs Apple 2FA).
- **Changing `cloudbuild.yaml`** — it already does the right thing; this FC only adds the trigger that invokes it.
- **PR-time deploy previews** — out of scope; `ci.yml` (FC-024) already runs tests on PRs.

## Proposed approach

Create exactly one 2nd-gen Cloud Build trigger against the existing connection (no new connection, no `cloudbuild.yaml` change):

```bash
gcloud builds triggers create github \
  --name=deploy-storybook-api-on-main \
  --project=ai-storybook-app-2025 \
  --region=us-central1 \
  --repository=projects/ai-storybook-app-2025/locations/us-central1/connections/github-connection/repositories/ai-storybook-app \
  --branch-pattern='^main$' \
  --build-config=cloudbuild.yaml \
  --included-files='backend/**,cloudbuild.yaml'
```

- `--included-files` is the load-bearing choice: with it, a merge that only touches `docs/**` or `mobile/**` produces no build. Only `backend/**` (or a change to the pipeline file itself) deploys.
- If trigger creation errors requiring a service account (newer gcloud enforces `--service-account` for 2nd-gen triggers), pass the existing Cloud Build runtime SA (the one that has been running deploys — discover via `gcloud builds list --format='value(serviceAccount)'` on the most recent successful build, or the project's `<PROJECT_NUMBER>@cloudbuild.gserviceaccount.com` / a dedicated deploy SA). Do NOT broaden IAM beyond what past deploys already used.

**Bootstrap deploy of current `main`:** because `--included-files` scopes to `backend/**`, the docs commit that publishes this FC will NOT trigger a build. So after creating the trigger, run it once against `main` to (a) validate the whole pipeline works and (b) ship the pending FC-037/041/028/016 backlog:

```bash
gcloud builds triggers run deploy-storybook-api-on-main \
  --project=ai-storybook-app-2025 --region=us-central1 --branch=main
```

Watch it to SUCCESS (test gate passes — backend suite is green at 166 tests), then confirm a new Cloud Run revision is serving.

## Risks & mitigations

- **A bad merge auto-ships to prod.** Mitigated by the `npm test` gate (a red suite aborts before build/deploy) + the two-reviewer merge process. Residual risk accepted for this stage; rollback = redeploy the prior Cloud Run revision (runbook). Revisit with a staging/approval gate (FC-009) as user count grows.
- **Trigger fires on unintended paths.** Mitigated by `--included-files=backend/**,cloudbuild.yaml`. Verify by inspecting the trigger after creation and confirming a docs-only commit does not start a build.
- **Secret/config drift on deploy.** `cloudbuild.yaml` pins `--timeout/--memory/--max-instances/--no-cpu-throttling`; env vars + secrets are already bound on the Cloud Run service and are preserved across `gcloud run deploy` (image-only update). No change here.
- **First auto-deploy differs from the last manual one.** The bootstrap run is the mitigation — it exercises the exact pipeline before relying on it for future merges.

## Execution

**Status:** Done
**Date:** 2026-07-08

**Correction — the premise was partly wrong.** The auto-deploy trigger **already existed**: `deploy-storybook-api` (2nd-gen, region `us-central1`, created 2026-04-04) fires on every push to `^main$` and runs `cloudbuild.yaml`. The regional build history confirms **every merge this session already auto-deployed** — e.g. FC-036 (`f97aa77`) + FC-040 (`17ada50`) at 06:45, FC-037 (`2a1a115`) 06:46, Wave A bookkeeping (`1c29de4`) 06:57, and Wave B's four at 07:48 (`5439c82`/`090a45e`/`23a278a` SUCCESS, `aab231e` FAILURE — see below). So FC-037/041/028/016 went live **at merge time**, not later.

**Root cause of the initial "zero triggers / nothing deployed" misread:** the diagnosis ran `gcloud builds triggers list` and `gcloud builds list` **without `--region`**, which defaults to the *global* region; the pipeline is *regional* (`us-central1`), so both came back stale (last global build 05-24, zero global triggers). Always pass `--region=us-central1` for this project's Cloud Build.

**What FC-043 actually delivered (net):**
- **Path filtering added** to the existing `deploy-storybook-api` trigger: `includedFiles = backend/**, cloudbuild.yaml` (via `gcloud beta builds triggers export`→edit→`import`, since the trigger predates path filtering). Before this, **every** push — including mobile-only and docs-only — triggered a full backend rebuild+deploy. That wasted builds and caused a real **concurrent-deploy FAILURE**: `aab231e` (FC-039, mobile-only) failed at 07:48 when four merges deployed simultaneously and collided at the Cloud Run step. FC-039's content was unaffected (mobile ships via EAS; the backend was unchanged), and later successful deploys superseded it — but path filtering removes this whole class going forward.
- **Removed an accidental duplicate trigger.** During the misdiagnosis a second trigger (`deploy-storybook-api-on-main`) was created and a redundant bootstrap build (`0bada00b`, `b8f0b33`) was run; both have been cleaned up (duplicate deleted; the bootstrap was a harmless re-deploy of already-deployed code).

**Final state (verified):** exactly one trigger — `deploy-storybook-api`, path-filtered to `backend/**` + `cloudbuild.yaml`. Live Cloud Run revision `storybook-api-00163-685` serving 100% traffic on the latest `main` backend. Future `backend/**` merges auto-deploy; mobile-only / docs-only merges do not. **Staging environment** + **manual-approval / promote gate** deferred to FC-009; Cloud Run revision rollback (FC-032 runbook) is the safety net.
