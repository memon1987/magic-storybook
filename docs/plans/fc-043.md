## Context

The backend has a deploy-ready pipeline that was never wired to fire automatically. Verified in GCP on 2026-07-08:

- `cloudbuild.yaml` (repo root) is a complete pipeline: `npm ci` → `npm test` (FC-032 test gate) → docker build → push to Artifact Registry → `gcloud run deploy storybook-api` with pinned `--timeout=3600`, `--memory=2048Mi`, `--max-instances`, `--no-cpu-throttling`.
- A 2nd-gen GitHub↔GCP connection exists: `github-connection` (region `us-central1`, state COMPLETE/Enabled), with `memon1987/ai-storybook-app` linked as a repository.
- **`gcloud builds triggers list` returns zero triggers.** Nothing invokes `cloudbuild.yaml` on push.

Consequence (the incident that motivated this): all of this session's backend work — FC-037 (input validation + text moderation + explicit `safetySettings`), FC-041 (vision-moderation image gate), FC-028 (aspect pin), FC-016 instrumentation — merged to `main` but was **not deployed**; the live Cloud Run revision serves a pre-merge image. Manual deploys are forgettable, and here the forgotten deploys were child-safety gates.

## Goals

- A merge to `main` that changes backend code automatically runs the `cloudbuild.yaml` test→build→deploy pipeline, so `main` and the live Cloud Run revision stay in sync.
- Backend changes only: docs-only or mobile-only merges must NOT trigger a backend rebuild/redeploy.
- Bootstrap: deploy the current `main` (which carries the unshipped FC-037/041/028/016 backlog) as part of enabling this, and use that run to validate the pipeline end-to-end.

## Non-goals

- **Staging environment / manual-approval gate** — deferred to FC-009. This ships auto-deploy-straight-to-prod, accepted for the current pre-launch/low-user stage. Rollback is the Cloud Run revision-rollback runbook (FC-032 `docs/runbooks/`).
- **Mobile/EAS CD** — EAS builds stay owner-triggered (no OTA; App Store submission needs Apple 2FA).
- **Changing `cloudbuild.yaml`** — it already does the right thing; this FC only adds the trigger that invokes it.
- **PR-time deploy previews** — out of scope; `ci.yml` (FC-024) already runs tests on PRs.

## Proposed approach

Create exactly one 2nd-gen Cloud Build trigger against the existing connection (no new connection, no `cloudbuild.yaml` change):

```bash
gcloud builds triggers create github \
  --name=deploy-storybook-api-on-main \
  --project=ai-storybook-app-2025 \
  --region=us-central1 \
  --repository=projects/ai-storybook-app-2025/locations/us-central1/connections/github-connection/repositories/ai-storybook-app \
  --branch-pattern='^main$' \
  --build-config=cloudbuild.yaml \
  --included-files='backend/**,cloudbuild.yaml'
```

- `--included-files` is the load-bearing choice: with it, a merge that only touches `docs/**` or `mobile/**` produces no build. Only `backend/**` (or a change to the pipeline file itself) deploys.
- If trigger creation errors requiring a service account (newer gcloud enforces `--service-account` for 2nd-gen triggers), pass the existing Cloud Build runtime SA (the one that has been running deploys — discover via `gcloud builds list --format='value(serviceAccount)'` on the most recent successful build, or the project's `<PROJECT_NUMBER>@cloudbuild.gserviceaccount.com` / a dedicated deploy SA). Do NOT broaden IAM beyond what past deploys already used.

**Bootstrap deploy of current `main`:** because `--included-files` scopes to `backend/**`, the docs commit that publishes this FC will NOT trigger a build. So after creating the trigger, run it once against `main` to (a) validate the whole pipeline works and (b) ship the pending FC-037/041/028/016 backlog:

```bash
gcloud builds triggers run deploy-storybook-api-on-main \
  --project=ai-storybook-app-2025 --region=us-central1 --branch=main
```

Watch it to SUCCESS (test gate passes — backend suite is green at 166 tests), then confirm a new Cloud Run revision is serving.

## Risks & mitigations

- **A bad merge auto-ships to prod.** Mitigated by the `npm test` gate (a red suite aborts before build/deploy) + the two-reviewer merge process. Residual risk accepted for this stage; rollback = redeploy the prior Cloud Run revision (runbook). Revisit with a staging/approval gate (FC-009) as user count grows.
- **Trigger fires on unintended paths.** Mitigated by `--included-files=backend/**,cloudbuild.yaml`. Verify by inspecting the trigger after creation and confirming a docs-only commit does not start a build.
- **Secret/config drift on deploy.** `cloudbuild.yaml` pins `--timeout/--memory/--max-instances/--no-cpu-throttling`; env vars + secrets are already bound on the Cloud Run service and are preserved across `gcloud run deploy` (image-only update). No change here.
- **First auto-deploy differs from the last manual one.** The bootstrap run is the mitigation — it exercises the exact pipeline before relying on it for future merges.
