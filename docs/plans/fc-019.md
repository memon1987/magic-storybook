## Context

We've now shipped FC-015 (Skia overlay) and FC-018 (refined overlay with soft halo + multi-shadow text). User feedback after FC-018: the overlay paradigm still doesn't feel right — "I'd like text closer to a true kids book that would be written and illustrated by an author."

Real kids' books co-design text + illustration: the author/illustrator knows where text will go and composes the art around it. No overlay panel. We've been moving the overlay around the problem rather than addressing it. **This plan re-evaluates whether the overlay paradigm itself is right, and what the alternatives look like in May 2026 — when image models have advanced materially since FC-002 (April 2026).**

User constraint (2026-05-16): be thoughtful about replacing Google's image models entirely. Don't trade a layout problem for a worse-image-quality problem.

## Goals

- Make a confident, evidence-based decision about whether to KEEP the Skia overlay paradigm, MOVE BACK to text-in-image (with a better-text model), or HYBRID.
- Avoid speculative migration. The text-in-image win is real on benchmarks; we should validate it on OUR story content + OUR character-consistency requirements before committing.
- Preserve the FC-013 character-reference investment if at all possible — character consistency is the other product-paramount feature alongside text quality.

## Non-goals (in the spike phase)

- No mobile changes. The spike is backend-only.
- No FC-015/018 Skia code removal. If text-in-image wins, that's a follow-up FC.
- No new vendor contract / billing setup beyond a free-tier or trial API key.
- Not migrating any production traffic; spike outputs are for comparison only.

## Options (with trade-offs)

### A. Stay on Skia overlay, keep iterating
- **Pros:** zero risk, zero new dependencies, JS-only iteration, 100% spelling accuracy.
- **Cons:** the user has rejected the paradigm twice (FC-015 → FC-018 → still wrong). Fundamentally, an overlay-on-top-of-art will never feel like "designed-into-the-illustration" the way real kids' books do.
- **Verdict:** rejected based on user feedback. If we go this way, we should commit to a more radical reskin (facing-page text + illustration like classic Random House readers, not overlay-on-illustration). Not the user's stated direction.

### B. Move BACK to Gemini 3 Pro Image; bake text in image (conservative)
- **Pros:** stay on Google (no vendor migration); same multimodal API we use today (FC-013 char refs work unchanged); 94-96% text accuracy (vs Flash's ~90%); Pro is now Google's forward image lane (Imagen 4 deprecating); proven model.
- **Cons:** ~5% pages will have a spelling error somewhere; Pro is ~2× the cost (~$0.13 vs $0.067) and ~2-3× the latency per image (~24-35s vs ~12-30s typical); no font control (Gemini picks the typography); we'd remove the FC-015/018 overlay machinery (~600 lines of code + mobile state).
- **Verdict:** lowest-risk way to get integrated text. The spelling issue is real but matches what real kids' books occasionally have (proofreading errors happen). Worth seriously testing.

### C. Hybrid: Gemini Flash for char refs + setting, Recraft V4 for page renders (specialized text)
- **Pros:** keeps FC-013 character ref investment (Gemini Flash already produces reliable model sheets); uses the only model purpose-built for multi-line illustration text on the page renders where it matters; can also use Recraft's "infantile_sketch" preset.
- **Cons:** TWO vendors in the pipeline (more failure surface); Recraft uses STYLE refs not character refs — can we pass Gemini's character sheets to Recraft and get character consistency? Unknown; need to test. Pipeline complexity grows.
- **Verdict:** best-case is "best of both worlds"; worst-case is "incompatible reference systems break character consistency." Real risk.

### D. Move fully to Recraft V4
- **Pros:** purpose-built for the use case (kids' book illustrations with multi-line text); top text-rendering model; reputable vendor; has inpainting + style transfer in one API.
- **Cons:** abandons Google's image lane entirely; loses FC-013 character-ref machinery (Recraft has style references but they're not character-specific); illustration quality may differ from current Gemini Flash output in subtle ways (we love Gemini's character-consistent watercolor style today).
- **Verdict:** the biggest swing. Defensible IF Recraft holds up on a comparison test, but big migration cost and we don't have evidence yet.

### E. Server-side text composition (Sharp/Canvas → composite text PNG onto Gemini's image)
- **Pros:** 100% font/spelling control; cheap; predictable; could use real picture-book fonts.
- **Cons:** SAME overlay paradigm we're trying to escape — just moves it from mobile Skia to backend Node. User has rejected this paradigm in mobile; it'll have the same "label slapped on" feel in backend.
- **Verdict:** rejected — solves the wrong problem.

### F. Two-stage hybrid: Gemini for scene (no text), then a second pass adds text via inpainting
- **Pros:** keeps Gemini's character consistency; uses a text-specialist model only for the text region.
- **Cons:** TWO API calls per page = +30-60s latency per page on top of current; complex masking/coordinate math; inpainted text often looks pasted-on (defeats integration goal); adds operational complexity.
- **Verdict:** rejected — too much added latency for uncertain integration benefit.

## Recommendation: SPIKE Options B + C in parallel (1-2 day effort)

Don't migrate anything. Run a 1-day backend experiment that generates THE SAME story (we already have one in the database from the sim testing) using:

1. **Variant A (control):** current pipeline — Gemini Flash + Skia overlay
2. **Variant B:** Gemini 3 Pro Image, text baked in (no Skia overlay on these outputs; text comes from the model)
3. **Variant C:** Recraft V4 for content pages (Gemini Flash still produces character refs for B; for C we test BOTH "no refs" and "Gemini char refs passed as style refs" to see if Recraft can use them)

Compare side-by-side on:
- **Text quality** — legibility, spelling accuracy, typography feel (integrated vs labeled)
- **Character consistency** — do the characters look the same across pages?
- **Illustration quality** — does the art still feel "right" for a kids' book (watercolor warmth, no uncanny valley)?
- **Latency** — wall-clock seconds per page + per story
- **Cost** — $ per page + per story

**Decision criteria** (decided BEFORE the spike, not after):

| If… | Then ship… |
|---|---|
| Pro Image text + char consistency feel author-designed, latency tolerable | **Option B** — migrate to Pro, remove FC-015/018 overlay machinery |
| Recraft text + illustration both clearly better than Pro, AND char refs work via style transfer | **Option D** — full Recraft migration (followup plan to remove FC-013's Gemini-specific machinery) |
| Recraft text wins but illustration / char consistency worse than Pro | **Option C** — hybrid (Gemini Flash for refs, Recraft for pages) IF we can get refs to work cross-vendor; otherwise Option B |
| Both Pro and Recraft text fail at our story content (e.g., still ugly multi-line layouts) | **Stay on current FC-018 path** — iterate further on Skia typography (per-position halo tuning, etc.) |

## Proposed approach (the spike itself)

### Backend-only changes (no mobile work):

1. **Add Pro Image as a swappable model** in `backend/src/services/gemini.ts`:
   - New env var `IMAGE_MODEL_PRO = 'gemini-3-pro-image-preview'`
   - New function `generateIllustrationPro(...)` that's a copy of `generateIllustration(...)` but with the Pro model + the LEGACY `pageText` path enabled (re-bakes text into image) + no `textPosition`/`soundEffects`/`emphasizedWords` (those become irrelevant when text is in-image).
   - Wire it behind a new env var `SPIKE_USE_PRO_IMAGE=true` so a single deploy can A/B between Flash+overlay and Pro+text-in-image.

2. **Add a thin Recraft client** in a NEW file `backend/src/services/recraft.ts`:
   - Direct fetch to Recraft's `https://external.api.recraft.ai/v1/images/generations` with auth header
   - Function signature mirrors `generateIllustration` for compatibility
   - **Model: V4 (current)** — the "ground-up rebuild" Feb 2026 release that improved on V3 specifically in text rendering and design control. We use V4 (not V4.1) for the spike because V4 is the quality-leaning tier (~$0.25/img); V4.1 (~$0.04/img) is the cost-optimized variant we'd consider in a SECOND spike pass if V4 wins on quality but cost is a concern.
   - Style preset: `digital_illustration/infantile_sketch` (kids' book preset; V3 introduced it, V4 retained it in the expanded style library)
   - Two variants: (a) text-only prompt, no refs; (b) text prompt + character-ref images attached (test whether Recraft V4 respects them as style guidance — V4 has stronger reference-image support than V3)
   - Env var `RECRAFT_API_KEY` (manual setup outside this PR)
   - Wire behind `SPIKE_USE_RECRAFT=true` env

3. **Add a spike route** `POST /api/spike/compare-story/:storyId` (auth-gated, dev-only):
   - Takes an existing story ID from Firestore
   - Re-generates ALL pages of that story under Variant B (Pro) → uploads to `stories/{id}/spike-pro/`
   - Re-generates ALL pages under Variant C (Recraft) → uploads to `stories/{id}/spike-recraft/`
   - Returns a JSON summary: per-page URLs from Variant A (existing) + B + C, plus latency + cost numbers
   - **Manual visual comparison happens in a browser** by opening the three URLs side-by-side. No mobile UI for the spike.

4. **No mobile changes**. Spike output is browser-viewed; the Skia overlay pipeline is untouched. If the spike fails, we revert the backend env vars and nothing in production changes.

## Risks & mitigations

- **Risk:** Recraft V4 doesn't accept character refs the way Gemini does → no char consistency across pages.
  - **Mitigation:** spike tests both "no refs" and "Gemini char refs as Recraft style refs". If neither works, we know Recraft is incompatible with our char ref machinery and falls down to "single-page consistency only" — that's a deciding data point.
- **Risk:** Pro Image latency is bad enough on a 4-page story that even with better text it's not viable.
  - **Mitigation:** spike captures actual wall-clock numbers per variant. If Pro takes 5+ min for a 4-page story, we have evidence to weigh against the quality win.
- **Risk:** the spike adds Recraft as a vendor dependency we then can't extract from.
  - **Mitigation:** Recraft is feature-flagged via env var; no production traffic touches it; revert is just `unset SPIKE_USE_RECRAFT`. We're not committing to Recraft until the decision phase.
- **Risk:** spending API budget on the spike.
  - **Mitigation:** small — 1 story × 4-6 pages × 2 variants = 8-12 Pro Image calls ($1-2) + 4-6 Recraft calls ($1-2). Negligible.
