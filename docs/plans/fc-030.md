## Context

Sub-FC of FC-017. Surfaced by the system-level retrospective adversarial review on 2026-06-23 ([docs/investigations/fc-017-retrospective-2026-06-23.md](../investigations/fc-017-retrospective-2026-06-23.md)). Four reviewers, four lenses; the distributed-systems reviewer (R1) found 3 BLOCKERs that the per-PR adversarial reviews of PRs #23, #26, #29 all structurally missed because they were cross-phase / cross-process races, not single-PR defects.

The common corruption is **duplicate page docs in the `stories/{id}/pages` subcollection** under any double-execution path (sweep ↔ takeover race, SIGTERM during success-batch, fire-and-forget catch clobbering a healthy worker). Auto-generated page-doc IDs at [backend/src/services/worker.ts:377](../../backend/src/services/worker.ts#L377) make the success-path `batch.commit` non-idempotent — two successful batches in different lifetimes produce two N-page sets. Mobile reader (orders by `pageNumber`) renders every page twice. Confirmed corruption class.

This plan closes the corruption class at three layers:

1. **Idempotency floor** — deterministic page-doc IDs make re-execution safe even when races sneak through.
2. **Race-window narrowing** — sweep uses a per-doc transaction with re-read; SIGTERM handler refuses to clobber `status='complete'`.
3. **Cross-process catch** — `fireWorkerInBackground`'s catch runs in a transaction that won't clobber a different live worker's `status='generating'`.

The idempotency floor is the single highest-leverage fix; it closes the corruption class for races we haven't found yet too.

## Goals

- Eliminate duplicate page docs in the `pages` subcollection under any double-execution path.
- Eliminate the sweep ↔ stale-lock-takeover race (R1 BLOCKER-1).
- Eliminate the SIGTERM ↔ success-batch.commit race writing `status='failed:sigterm'` over a complete story (R1 BLOCKER-2).
- Stop `fireWorkerInBackground`'s catch from clobbering a different live worker's `status='generating'` (R1 BLOCKER-3 — UX flicker, not corruption, but worth fixing while we're in the area).
- Add integration tests (Firestore emulator) for the worker concurrency-critical paths so regressions are caught at PR time.

## Non-goals

- Mobile-side hardening (library live-update, navigatedRef stuck-state, retry budget) — those are FC-031.
- Ops floor (Firestore PITR, alerting, max-instances pin, runbooks) — those are FC-032.
- Migrating the sweep auth from static bearer token to OIDC — FC-032.
- Refactoring the architecture to Cloud Tasks (R1 system-level critique) — out of scope; the in-process Cloud Run worker pattern stays, this FC just hardens it.

## Proposed approach

### Change 1 — Deterministic page-doc IDs (idempotency floor, ~1 LOC)

[backend/src/services/worker.ts:377](../../backend/src/services/worker.ts#L377):

```diff
- const pageRef = storyRef.collection('pages').doc();
+ const pageRef = storyRef.collection('pages').doc(String(page.pageNumber));
```

`batch.set(pageRef, ...)` becomes idempotent — two successful batches in different lifetimes write the same doc IDs with identical content, last-write-wins on identical bytes. The duplicate-pages corruption class is closed at this layer regardless of which upstream race fires. This is the single most important change in this plan.

**Migration:** existing complete stories have auto-id'd page docs (e.g., `pages/abc123XyZ`). The new code writes `pages/1`, `pages/2`, …. **No production data is corrupted by this change** (existing docs aren't touched; only re-runs of in-flight stories at the moment of deploy would write to `pages/1`-style IDs). The reader (mobile + `GET /api/stories/:id`) queries the subcollection with `.orderBy('pageNumber')` — doc IDs don't matter to the reader. **No migration required.**

### Change 2 — Sweep transactional re-read (closes BLOCKER-1 race window)

[backend/src/routes/admin.ts:73-101](../../backend/src/routes/admin.ts#L73-L101):

Replace the bulk `batch.update` with per-doc `runTransaction` blocks. Inside each transaction, re-read the doc and only write the failed-state if the predicate still holds — i.e., `workerHeartbeatAt` (or `createdAt` for queued docs) is STILL older than the cutoff.

Cost: N transactions instead of 1 batch (N small reads + N small writes). At expected sweep-size (≤10 orphans per 10-min window in normal operation), the latency hit is ~1-2s per sweep — well under the 180s `attemptDeadline`.

Add `.limit(100)` to both queries (R3 M-6) — under a regional outage that flips many docs to generating, we don't want to pull a massive snapshot in one go. The next cron tick picks up the rest.

### Change 3 — SIGTERM-aware finalize (closes BLOCKER-2 race window)

[backend/src/services/worker.ts:488-513](../../backend/src/services/worker.ts#L488-L513):

The SIGTERM handler should use a transaction that refuses to overwrite `status='complete'` or `status='failed'` (the latter because the worker's own catch may have already written a more specific failureReason). Right now it does a blind `update({status:'failed:sigterm', ...})` which races with an in-flight success-path `batch.commit`.

Combined with Change 1 (deterministic page IDs), even if this race somehow still fires, the second worker's re-execution writes pages to the same IDs — no duplicates.

### Change 4 — `fireWorkerInBackground` transactional catch (closes BLOCKER-3 flicker)

[backend/src/routes/stories.ts:95-105](../../backend/src/routes/stories.ts#L95-L105):

Replace the re-read-then-update with a transaction that refuses to clobber a doc owned by a different live worker (`workerId` set) or a terminal state (`complete`/`failed`).

### Change 5 — Tests

The four BLOCKERs are concurrency-class defects. Add the lightest-weight harness that actually exercises them:

- **Unit test (in-memory):** assert deterministic page-ID generation by running the page-id derivation twice with identical inputs.
- **Behavior test against an in-memory Firestore double:** simulate the sweep ↔ takeover race using a `vi.fn()`-backed `runTransaction` that records ordering; assert sweep aborts when heartbeat is fresh.
- **Behavior test:** SIGTERM handler against `status='complete'` is a no-op.
- **Behavior test:** `fireWorkerInBackground` catch against a doc with `workerId` set leaves status alone.

If a full Firestore emulator setup grows beyond ~80 LOC of test infra, defer to a separate FC (R1 MEDIUM-3 — "stand up Firestore emulator + Vitest integration suite") and ship this FC with the lighter-weight harness above.

## Risks & mitigations

- **Risk: per-doc sweep transactions are slower than a bulk batch.** Sweep at scale could exceed the 180s `attemptDeadline`.
  - Mitigation: `.limit(100)` on each query + the next cron tick picks up the rest. Expected normal sweep is ≤10 orphans/10-min.
- **Risk: deterministic page IDs collide between two stories.** They don't — IDs are scoped to `stories/{storyId}/pages/{pageNumber}`. Collisions only happen between re-runs of the same story, which is exactly the idempotency we want.
- **Risk: tests against a mocked Firestore can't catch real distributed-systems bugs.** True — the mocked harness gives us regression-prevention on the specific paths, not exhaustive concurrency proof. The deferred Firestore-emulator FC will tighten this.
