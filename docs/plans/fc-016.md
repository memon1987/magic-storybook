## Context

FC-016 was originally framed around page-parallelization. FC-020 shipped that lever
(`docs/plans/fc-020.md`, merged 2026-05-24): pages now run K sequential anchors + the rest
in a bounded-concurrency parallel batch. On the validated 8-page run the page stage was
~62s. The **same run** spent **~332s on the character-reference stage** (3 char refs + a cast
lineup, one ref hitting a 503 and taking ~331s end-to-end). The remaining ~46s was story
text + Firestore I/O.

That makes char-ref generation the unambiguous bottleneck. The FC-016 FC entry was
re-scoped on 2026-05-24 around this stage; this plan executes the re-scope.

This is a **research-first** plan in the spirit of FC-002
(`docs/investigations/fc-002-latency-benchmark-2026-04-28.md`). Phase 1 establishes a
defensible baseline; Phase 2-4 pick a lever from that evidence. Do **not** start any
implementation lever in Phase 2 without Phase 1's numbers in hand — the 332s figure is one
sample. We don't know yet if it's typical, an outlier driven by the single 503, or a moving
target on Gemini's load.

This plan deliberately does NOT re-open page parallelization. FC-020 owns that.

## Coordination with FC-017 (reliability)

FC-016 and FC-017 are designed to run **in parallel** — different layers, different goals (this plan reduces call-level latency; FC-017 buys orchestration-level durability). Same files get touched (`gemini.ts`, `stories.ts`, `textVerify.ts`) but at different sites; no architectural coupling.

Two practical coordination points:

1. **Share Phase 1 instrumentation.** This plan's Phase 1 (per-stage structured JSON logs) and FC-017's Phase 1 (per-phase memory + timing + Gemini call wrapper + request-tagged logs) overlap substantially. Land them as **one shared instrumentation PR** that satisfies both Phase 1 exit criteria at once. Avoids two near-identical logging refactors stepping on each other.
2. **Prefer FC-017's Phase 2 before this plan's Lever A1 (cache).** The cache lookup naturally lives at the Firestore-aware boundary FC-017 Phase 2 introduces (per-char-ref persistence). Doing FC-017 Phase 2 first saves a small refactor here. Not a hard blocker — reversed order works, just adds ~½ day of weaving. **Lever E1 (per-call timeout) is independent of FC-017 and can ship at any point** — it's the cheapest win and unblocks itself.

## Goals

- Measured baseline: p50 / p95 / p99 of **end-to-end wall-clock** and **char-ref stage
  wall-clock** across ≥ 5 fresh production-equivalent stories (mix of 1, 2, 3 character
  counts), captured with the FC-002 method so the numbers are comparable.
- A ranked lever list (caching/reuse, fewer refs, downscaled refs, faster ref path, faster
  503 circuit-break) with **expected leverage × cost** scored from Phase 1 data, not from
  a priori guesses.
- Ship the top one or two levers behind a flag, A/B-measured against the Phase 1 baseline,
  with **explicit go/no-go criteria** (latency target + consistency floor).
- Net result: p50 char-ref stage ≤ **90s** (from ~332s in the FC-020 measurement),
  p95 ≤ **180s**, with OCR-clean rate and visual consistency at parity with FC-020.

## Non-goals

- **Page parallelization, anchor count K, OCR thresholds.** FC-020 owns those.
- **Async / resume / job model** — that's FC-017. Cache hits will interact with FC-017's
  resume story (a resumed job should treat already-rendered refs as cache hits) but we
  do not block on FC-017 nor refactor towards it here.
- **Switching the image model** (Pro / Recraft / other). Rejected by FC-019/020.
- **Reducing the number of pages or the writing-style fan-out.** Scope is char refs only.
- **Cloud Run cold-start tuning** (min instances etc.). Separate concern; included only
  as a noted variable in Phase 1 measurement.

## Proposed approach

Four phases, each gates the next. Each phase must commit numbers (a table, like the FC-002
investigation) before Phase N+1 starts.

### Phase 1 — Measurement (no production code change)

Goal: a comparable-to-FC-002 baseline table for the **post-FC-020** pipeline, decomposed
by stage. Today we have one data point (440s total / ~332s char-ref); five is the floor.

1. **Stage-level instrumentation.** Add structured JSON log lines at every stage boundary
   in `backend/src/services/gemini.ts` and `backend/src/routes/stories.ts`:

   ```
   { event: 'stage_done', stage: 'story_text' | 'char_ref' | 'cast_ref' | 'title_page'
                                | 'anchor_pages' | 'parallel_pages',
     storyId, pageCount, charCount, latencyMs, attempts, retries5xx, model, ts }
   ```

   Replace/augment the existing free-text `console.log` lines. Per-char-ref logging
   already exists; add per-attempt structured emission so we can separate the 503-retry
   tail from the green-path latency. **Implementation note:** this is the only Phase 1
   code change, < 80 lines, lands as its own small PR ahead of Phase 2.

2. **Baseline sweep.** Generate 5 fresh 8-page stories spread across at least two
   calendar days and two times of day (Gemini load varies — FC-002 observed 18× tail
   variance run-to-run). Parameterize:
   - char count: 1, 2, 2, 3, 3 (cast lineup only fires at ≥ 2)
   - art style: mix at least 3 of the 6 styles (rules out per-style anomalies)
   - same backend revision, same model (`gemini-3.1-flash-image-preview`)

3. **Tabulate** in `docs/investigations/fc-016-charref-baseline-2026-MM-DD.md` (same
   layout as the FC-002 report): per-stage p50/p95/p99 in seconds, char-ref attempt
   counts, 5xx retry distribution, end-to-end wall-clock, ratio of char-ref to total.

4. **Decision criteria for Phase 2:**
   - If p50 char-ref ≤ 60s and p95 ≤ 120s, the 332s figure was an outlier. **Stop** —
     write that up, downgrade the FC, no implementation.
   - If p95 char-ref ≥ 180s OR a single ref's p99 attempt latency ≥ 200s, the bottleneck
     is real and we proceed to Phase 2.

### Phase 2 — Lever enumeration & ranking

For each lever below, Phase 1 data tells us its **upper-bound payoff**. Rank by
`expected_seconds_saved_at_p50 / engineering_days`. Lock the top 2 to Phase 3.

**Lever A — Character-ref caching (highest expected leverage).** Refs are deterministic-ish
functions of `(character_name, character_description, art_style)`. A second story with
the same `(animalType, artStyle)` and a textually-similar character sheet can plausibly
reuse the rendered ref instead of regenerating. Two scopes:

  - **A1 — Intra-user reuse.** Most parents will generate multiple stories featuring the
    same child + same favorite animal. Key: `sha256(art_style + child_name + animal +
    normalized(character_description))`. Cache lookup in Firestore (`charRefCache`
    collection) before calling `generateCharacterReference`; on hit, skip the Gemini call
    entirely and reuse the GCS image URL + re-download bytes for multimodal refs.
  - **A2 — Cross-user reuse for the non-personalized character.** The favorite-animal
    sidekick (when not the protagonist) is highly cacheable across users — a
    "watercolor friendly hamster" looks the same regardless of which child the story is
    for. Same key minus child_name.

  Expected payoff: **massive** if cache hit rate ≥ 50%. Each hit elides one 4-30s+ image
  call (and removes its 503-retry tail risk entirely). Phase 1 must report cache-hit
  *opportunity* — for each generated story, was the char description close enough to a
  prior story's that a cache would have hit? Measure with normalized-description hashing
  on the 5 baseline stories' existing chars in Firestore.

**Lever B — Fewer refs.** Currently the pipeline generates N per-character model sheets
*and* (when N ≥ 2) a cast lineup. Two sub-levers:

  - **B1 — Drop per-character sheets when cast lineup is present.** The cast lineup
    already shows every character at correct relative scale. Per-character sheets add
    front/three-quarter/action views the cast doesn't. Hypothesis: for ≥ 2-character
    stories, cast-lineup-only is enough. Saves N image calls (the cast lineup already
    runs in parallel with title page, so cutting per-char sheets cuts the WHOLE step 1).
  - **B2 — Conditional cast lineup.** Currently cast fires whenever `characters > 1`.
    A 2-character story with one tiny animal + one child has cheaply-described relative
    scale; the cast may be unnecessary. Lower-leverage variant of B1.

  Expected payoff at p50: cutting N parallel calls doesn't reduce wall-clock by N×
  because they're parallel — but it cuts the **probability of any one of them hitting
  the 503-retry tail**, which is what dominates p95. With 3 calls each at ~5% chance of
  a 60s+ retry, dropping to 1 call cuts the tail-hit probability ≈ 3×.

**Lever C — Faster ref path.** Char refs are not user-visible — they're internal anchors.
Investigate:

  - Lower-resolution / smaller-output Gemini variant if exposed by `@google/genai` (check
    request config for image-size parameters on `gemini-3.1-flash-image-preview`).
  - Simplified prompts (the current `buildCharacterReferencePrompt` is ~25 lines; a
    minimal "single character, white bg, 3 poses, style X" may produce the same
    embeddable anchor with lower per-call latency, though this is unproven).
  - Skipping the OCR verify on refs (refs have no text — already true, confirm).

  Lower expected leverage than A/B; included for completeness. Phase 1 per-attempt
  latency tells us if green-path char-ref calls are themselves slow (they shouldn't be —
  they're text-only, no multimodal input, no baked text).

**Lever D — Downscaling refs fed back into page calls.** Each page call attaches char
refs + cast + K anchors as multimodal inputs. If those are 600KB-1MB PNGs, downscaling
to ~256-384px before re-attaching could reduce per-page upload + Gemini-side processing
time. This is a **page-stage** lever masquerading as a char-ref lever — but it lives in
the char-ref bytes, so it belongs here. Low risk (we control the downscale), needs
A/B on visual consistency.

**Lever E — Faster 503 circuit-break.** The 331s outlier in the FC-020 run was one ref's
retry chain. `MAX_RETRIES = 3` with jittered exponential backoff (2s, 4s, 8s) shouldn't
sum to 331s — meaning the actual *single-call* tail latency was the killer, not the
retry schedule. Two sub-levers:

  - **E1 — Per-call timeout.** Wrap each `ai.models.generateContent` call in a 60s
    `AbortController` race. If it hasn't returned by 60s, abort and retry — caps the tail.
  - **E2 — Speculative parallel retry.** On the second attempt, fire two parallel requests
    and take the first to return. Doubles Gemini cost on retry only (already < 0.1% of
    calls); caps tail at the faster-of-two latency.

  E1 is cheap (a dozen lines) and ALWAYS helps the p95/p99 regardless of which other
  levers win. **Likely landed first**, even before A/B/C/D, because it bounds the worst
  case the rest of the work is measured against.

### Phase 3 — A/B variants

For each of the top 2 levers from Phase 2:

- **Implementation:** flag-gated path in `backend/src/services/gemini.ts`. Env var per
  lever (e.g. `FC016_CHARREF_CACHE=true`, `FC016_CAST_ONLY=true`). Default off in
  production; on for the A/B sweep only.
- **Sweep size:** 5 stories per variant, matched on (char count, art style) to one of
  the Phase 1 baseline stories. Same time-of-day buckets.
- **Consistency metric (mandatory — char-ref's whole job is consistency):**
  - **Quantitative:** OCR clean rate on the pages (FC-020's existing `[TEXT-VERIFY]`
    recall/precision per page). If recall × precision drops > 5pp from baseline, the
    variant is rejected on consistency, latency win irrelevant.
  - **Qualitative:** human eyeball pass — open the 5 stories side-by-side with their
    baseline twins. Are the characters recognizably the same person across pages?
    Three-judge rubric (1-5 each on `character_identity`, `relative_scale`,
    `style_continuity`). Baseline mean - variant mean > 0.7 on any axis = reject.
- **Latency target per variant:**
  - Lever A (caching): on a story whose chars cache-hit, char-ref stage ≤ 5s
    (Firestore lookup + GCS bytes download only). Cold-start: same as baseline.
  - Lever B (fewer refs): cuts step 1 calls in half (or more); target p50 char-ref ≤ 30s.
  - Lever E (faster circuit-break): p99 single-call ≤ 90s (the 60s timeout + one retry).
    p50 unchanged.
- **Tabulate** in `docs/investigations/fc-016-ab-results-2026-MM-DD.md` with the same
  schema as the baseline report.

### Phase 4 — Pick a winner and ship

**Commit criteria for merging a lever into production (default-on):**

1. Latency target hit on the variant sweep (Phase 3 numbers).
2. Consistency floor held (OCR-clean ≥ baseline - 5pp AND rubric ≤ baseline + 0.7
   on each axis).
3. No new failure modes (no observed regression in retry rate, story-gen error rate,
   timeout rate).
4. Implementation passes adversarial review (per `docs/plans/fc-020.md` precedent).

**Default lever ordering (subject to Phase 2/3 data):**

- **Ship E1 (per-call 60s timeout) first, unconditionally.** Cheap, strict win on p99,
  doesn't depend on the rest. ~1 day.
- **Then ship A1 (intra-user char-ref cache)** if Phase 1 shows hit-opportunity ≥ 40%
  on retro data. ~3-4 days (Firestore schema, cache lookup, hash key, byte re-download
  path, test coverage).
- **Then evaluate A2 / B1** based on remaining gap to the 90s/180s targets.

If the Phase 3 A/B for the lead lever fails consistency, **ship E1 alone and re-scope.**
We will not ship a latency win that visibly degrades character consistency — FC-020's
whole architecture exists to hold that floor.

- `MAX_CHARACTER_REFS` cap — preserved across all levers; cache lookups respect the same
  cap.
- FC-002's measurement table layout — reused verbatim for the Phase 1 / Phase 3 reports.
- Existing GCS layout `stories/{id}/character-refs/{name}-{uuid}.{ext}` — cache hits
  reuse the original story's GCS object (no new copy); store the GCS path as the cache
  value, not a duplicated blob.
- Existing `characterSheets` persistence on the story doc (`routes/stories.ts:153`) —
  becomes the source-of-truth for cache-key normalization (we already persist the textual
  sheet, so we can dedupe on it).

## Risks & mitigations

- **Risk: Phase 1 shows the 332s was a one-off and there's no real bottleneck.**
  *Mitigation:* the plan explicitly stops at Phase 1 in that case. Five samples cost
  ~$3 in Gemini fees; cheap insurance against speculative optimization.
- **Risk: Char-ref cache delivers stale/wrong refs (description text shifted slightly,
  cache returns the old image, character drifts).** *Mitigation:* cache key includes the
  full normalized description; near-miss textual descriptions miss the cache and
  regenerate. We do NOT do fuzzy-match. Better to miss the cache than serve a wrong char.
- **Risk: Fewer refs (B1) regresses character consistency on stories with 3+ characters.**
  *Mitigation:* Phase 3 consistency floor is hard — the rubric kills B1 if it fails.
- **Risk: Per-call 60s timeout (E1) cuts off green-path calls that legitimately need
  >60s.** *Mitigation:* Phase 1 data tells us the green-path p99 — set the timeout 1.5×
  above that, not at an arbitrary 60s. Tune based on evidence, not guess.
- **Risk: Cross-user cache (A2) leaks identity across stories** — e.g., one user's hamster
  ref appears in another user's story. *Mitigation:* only cache the **non-personalized**
  sidekick (favorite animal NOT == childName-shaped), and only when no
  child-identifying fields are in the description. Conservative: ship A1 first, A2 only
  after A1 proves out.
- **Risk: FC-017 lands an async/resume model and changes where caching belongs
  (job-level vs ref-level).** *Mitigation:* keep this plan's cache at the ref-level
  (`(art_style, normalized_description)`), not job-level. FC-017's resume can reuse the
  same cache without refactor. Noted as coordination point, not blocker.
- **Risk: Downscaling refs (D) reduces visual fidelity transmitted to page calls.**
  *Mitigation:* A/B with the consistency rubric. If 256px refs hold, ship; if not, keep
  full-res.

## Rollout

- **Phase 1 PR (instrumentation only):** small, < 80 lines, structured logs. Deploy to
  production, capture 5 stories over ≥ 2 days, file the baseline investigation. Phase 1
  gates the rest.
- **E1 PR (per-call timeout):** small, ships behind `FC016_CHARREF_CALL_TIMEOUT_MS`
  (default unset = current behavior; set to the Phase 1-derived value to enable).
  Default it to on after one week of clean logs.
- **A1 PR (intra-user cache):** medium, new Firestore collection + cache helpers + test
  coverage. Flagged via `FC016_CHARREF_CACHE=true` on the staging service first, monitor
  hit rate + char-consistency over ≥ 5 fresh stories, then enable in production.
- **Monitor after each deploy:** Cloud Run request duration p50/p95/p99 by stage (using
  the new structured logs); cache hit-rate dashboard; OCR-verify rates (must not move);
  story-gen error rate.
- **Rollback:** each lever is independently flagged. Toggle env var off, redeploy
  revision; no schema migration risk (cache is read-through, missing rows just miss).

## Open questions

- **What's the right cache TTL?** Char refs are deterministic-ish, but Gemini's model
  weights change over time and an old cache hit might style-mismatch a freshly-generated
  page. Lean: 90 days, configurable. Decide from Phase 3 visual-rubric data.
- **Should cache lookups be GCS-based instead of Firestore-based?** GCS object existence
  check is one read, but Firestore lets us index on normalized-description. Lean:
  Firestore for the index, GCS for the bytes (current layout).
- **For Lever B1 (cast-only), do we still need to ATTACH individual char refs to page
  calls, or is the cast lineup enough as the sole anchor?** Phase 3 visual-rubric data
  answers this; pre-decision: keep per-char refs attached on page calls even if we
  skip *generating* a separate model sheet by reusing the cast crop. (Future variant.)
- **Does Gemini's `@google/genai` SDK expose any per-call timeout or
  image-size config we're not using?** Verify in Phase 2; if yes, E1 becomes a
  one-liner.
- **Cross-user cache (A2): is "shared friendly animal" actually identity-leaky if the
  textual description is generic ("a friendly orange hamster")?** Probably not. But
  validate before shipping A2.
