## Context

Sub-FC of FC-017. The cloud-ops reviewer (R3) in the 2026-06-23 system-level retrospective ([docs/investigations/fc-017-retrospective-2026-06-23.md](../investigations/fc-017-retrospective-2026-06-23.md)) found that **FC-017's data-layer + distributed-systems work is sound, but the operational posture surrounding it is essentially zero**:

- No Firestore backups, no point-in-time recovery — next data-corruption bug is unrecoverable.
- `--max-instances=20` is set on the live revision as a manual annotation but not pinned in `cloudbuild.yaml` — next deploy that touches scaling silently regresses to the default `1000`.
- Zero alerting / monitoring — Phase 1's structured instrumentation lands in Cloud Logging and is never read. The exact 2026-05-12 failure mode would still take days to discover.
- Cloud Scheduler doesn't actually retry on failure (`retryConfig.maxRetryDuration=0s`).
- Cloud Run secret rotation is broken-by-default (4-step ritual undocumented; container caches at start).
- Static bearer token for sweep is readable to any Project Viewer via `cloudscheduler.jobs.get`.
- CI runs no tests before deploy.
- Zero runbooks for any of the 12 operational scenarios audited.

This plan closes the ops floor enough to claim "complete and hardened FC-017."

## Goals

- Firestore PITR enabled + daily backups scheduled (R3 B-1).
- `--max-instances=20` pinned in `cloudbuild.yaml` (R3 B-2).
- Baseline alerting in place: notification channel + 3-4 log-based-metric policies for Cloud Run errors / Scheduler failures / build failures / worker failure-rate (R3 B-3).
- Cloud Scheduler retry config corrected (R3 B-4).
- CI test gate in `cloudbuild.yaml` so a broken test suite doesn't deploy (R3 H-5).
- Cloud Scheduler ↔ sweep endpoint migrated from static bearer token to **OIDC**, retiring `SWEEP_AUTH_TOKEN` entirely (R3 H-2/H-3).
- `docs/runbooks/` directory with one .md per operational scenario (R3 H-1).

## Non-goals

- Backend correctness fixes (FC-030 corruption hotfix).
- Mobile-side hardening (FC-031).
- Cost dashboards / billing alerts (defer; cheaper to set up after first month of post-FC-017 cost data).
- Log-based metrics for `event:"stage_done"` + Cloud Monitoring dashboard (defer to a follow-up FC; the alerting baseline in this plan suffices to detect *failure* events, just not to chart *latency distributions*).
- Firestore emulator + integration test infra (R1 MEDIUM-3 — separate FC).

## Proposed approach

### Change 1 — Firestore PITR + daily backups

Two `gcloud` commands:

```bash
# Enable 7-day point-in-time recovery on the default database
gcloud firestore databases update '(default)' --enable-pitr

# Create a daily backup schedule with 7-day retention
gcloud firestore backups schedules create \
  --database='(default)' \
  --retention=7d \
  --recurrence=daily
```

These are one-time configuration changes; they're documented in this plan + the runbook in Change 7 below but don't ship as code. The investigation captures the rationale.

Cost: PITR is ~$0.36/GiB-month for the 7-day window; daily backups are charged similarly. At current dataset size (~MB scale), monthly cost is well under $1.

### Change 2 — Pin `--max-instances=20` in `cloudbuild.yaml`

Two-line addition to the `gcloud run deploy` args block:

```diff
   args:
     - 'run'
     - 'deploy'
     - 'storybook-api'
     - '--source=.'
     ...
     - '--no-cpu-throttling'
+    - '--max-instances=20'
```

While there, also explicitly set `--min-instances=0` so future intentional warm-instance changes are visible in `git diff`.

### Change 3 — Baseline alerting

Three Cloud Monitoring alert policies + one notification channel. Done via `gcloud` (one-time config); document in the runbook (Change 7).

**Notification channel:**
```bash
gcloud beta monitoring channels create \
  --display-name="zeshan@tkzmgroup.com" \
  --type="email" \
  --channel-labels=email_address=zeshan@tkzmgroup.com
```

**Alert policies (all 5-minute windows, alert on threshold breach):**

1. Cloud Run error rate > 5/min: filters `severity=ERROR resource.type="cloud_run_revision" resource.labels.service_name="storybook-api"`.
2. Cloud Scheduler job failures: `metric.type="cloudscheduler.googleapis.com/job/attempt_count"` filtered to job_id="sweep-orphans" + FAILED.
3. Cloud Build failures: `metric.type="cloudbuild.googleapis.com/build/status"` filtered to FAILURE.
4. (Optional) Worker failure rate: a log-based metric on `event:"stage_done" stage:"total" outcome:"failure"` > 3/hour.

The setup is `gcloud`-driven; documented in the runbook so future channel/policy adjustments don't need to re-derive the syntax.

### Change 4 — Cloud Scheduler retry config

```bash
gcloud scheduler jobs update http sweep-orphans \
  --location=us-central1 \
  --max-retry-attempts=3 \
  --min-backoff=30s \
  --max-backoff=5m
```

The sweep endpoint is idempotent — retry is safe. Combined with Change 3's alerting, real failures get both auto-recovery and visibility.

### Change 5 — CI test gate in `cloudbuild.yaml`

Add a test step before the existing build step:

```yaml
- name: 'node:20'
  entrypoint: 'npm'
  args: ['ci']
  dir: 'backend'
- name: 'node:20'
  entrypoint: 'npm'
  args: ['test']
  dir: 'backend'
```

Cloud Build steps run sequentially by default; a non-zero exit from `npm test` fails the build (and the deploy never happens). The previous revision keeps serving — combined with Change 3 alert on build failures, the team learns immediately.

### Change 6 — OIDC sweep auth

Replace the static bearer token with Google-issued OIDC tokens. The Cloud Scheduler job mints them; the Cloud Run endpoint verifies via Google's standard middleware.

**Backend changes** ([backend/src/routes/admin.ts](../../backend/src/routes/admin.ts)):

Replace `checkSweepAuth`'s `Authorization: Bearer ${SWEEP_AUTH_TOKEN}` check with OIDC verification:
- Extract the JWT from `Authorization: Bearer <jwt>`.
- Verify the JWT signature against Google's JWKS endpoint (use `google-auth-library` — already a transitive dep via `@google-cloud/firestore`).
- Verify the `aud` claim matches the Cloud Run service URL.
- Verify the `email` claim matches the expected service account (the one we configure on the Scheduler job).

```bash
# Configure the Scheduler job to use OIDC
gcloud scheduler jobs update http sweep-orphans \
  --location=us-central1 \
  --oidc-service-account-email=sweep-scheduler@ai-storybook-app-2025.iam.gserviceaccount.com \
  --oidc-token-audience=https://storybook-api-983903024759.us-central1.run.app/api/admin/sweep-orphans \
  --remove-headers=Authorization
```

**Cleanup:** after the new code is deployed AND the Scheduler is updated AND a smoke test confirms OIDC works, delete the Secret Manager secret + drop the `SWEEP_AUTH_TOKEN` env var binding from Cloud Run.

**Secret leak class fully closed:** there's no shared static credential anywhere. The OIDC tokens are short-lived (~1 hour) and signed by Google — even a Project Viewer leaking one can't replay it past expiry.

## Risks & mitigations

- **Risk: Firestore backups + PITR adds ongoing cost.** Cost is trivially small at current dataset size (<$1/month).
- **Risk: pinning `--max-instances=20` blocks legitimate large bursts.** The current ceiling is the engineered safety; any change should be a deliberate plan-file decision, not a silent annotation drift. The pin is the right default.
- **Risk: alerting on `severity=ERROR` Cloud Run logs creates noise.** True for the first week. Triage: every alert that fires gets a runbook entry + adjustment to the policy. Iterate to noiseless.
- **Risk: CI test gate breaks the deploy pipeline if a test is flaky.** The 51 existing tests are unit-only and deterministic; flakiness risk is low. Worst case: skip the broken test with a `vi.skip` + open a follow-up to fix it, restoring the deploy ability.
- **Risk: OIDC migration deploy-order screws up.** The OIDC backend code must deploy BEFORE the Scheduler is switched, OR vice versa, but not both at once. Mitigation: in the backend, accept BOTH static bearer AND OIDC for a transition window (Stage 1); switch Scheduler to OIDC (Stage 2); remove static bearer code (Stage 3). Each stage is a separate small commit.
- **Risk: runbooks become stale.** Mitigation: each runbook starts with `Last verified: YYYY-MM-DD`; whoever runs through it updates the date. Stale runbooks worse than no runbooks is a known anti-pattern; pair with the alert that triggers them so they get exercised.
