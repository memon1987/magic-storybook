## Context

`mobile/services/firebase.ts` and `mobile/services/api.ts` had Firebase web config and the Cloud Run API URL hardcoded into source. Two motivations to externalize:

1. **Pre-launch hygiene.** App Store review and general code-quality conventions discourage hardcoded API endpoints in source. Externalized configs are also easier to flip between staging and prod when FC-009 (staging environment) lands.
2. **Multi-environment readiness.** When we cut a staging Cloud Run service or a separate Firebase project, swap-by-env-var is the cleanest path; baked-in URLs require a rebuild per environment.

**Not a security incident.** Firebase web API keys are designed to be public — Firestore Security Rules enforce auth, not key obscurity. The Cloud Run URL is also publicly addressable. The previously-baked values are not being rotated; this is a code-quality / convention fix.

## Goals

- Replace hardcoded `firebaseConfig` object in `services/firebase.ts` with `EXPO_PUBLIC_FIREBASE_*` env vars
- Replace hardcoded `API_URL` in `services/api.ts` with `EXPO_PUBLIC_API_URL` env var
- Fail loudly at module load if any required var is missing (clearer than the Firebase SDK's downstream errors)
- Commit `mobile/.env.example` so new contributors / future CI know exactly which vars to populate
- Update `CLAUDE.md` to document the env vars and the rationale

## Non-goals

- Rotating the existing Firebase API key or Cloud Run URL (not a leak)
- Switching to `app.config.js` for dynamic config (not needed — `EXPO_PUBLIC_*` works through Expo's CLI bundling, no app.config.js change required)
- Creating a staging environment (FC-009 territory)
- Moving backend secrets — backend already uses Cloud Run env vars + Secret Manager, no change needed
- Encrypting the `.env` file at rest

## Proposed approach

**`services/firebase.ts`** — replace the inline `firebaseConfig` constant with an object built from `process.env.EXPO_PUBLIC_FIREBASE_*` lookups via a tiny `requireEnv(name)` helper. The helper throws with a clear message naming the missing var if the value is `undefined`.

**`services/api.ts`** — same pattern for `API_URL`, but inline at the top of the module since there's only one var.

**`mobile/.env.example`** — committed template with placeholder values (e.g. `your-firebase-web-api-key`) and a comment explaining the security model (Firestore Rules enforce auth, not key obscurity).

**`mobile/.env`** — populated locally for the developer running the app. Already gitignored under the existing `.env` rule. Not committed.

**`CLAUDE.md`** — refresh the Mobile env var section with the full list and the rationale paragraph.

## Reuse

- Existing `mobile/.gitignore` already covers `.env`, `.env.local`, `.env.*.local`. No gitignore changes needed.
- Existing Expo CLI behavior: `EXPO_PUBLIC_*` vars from `mobile/.env` are inlined into the JS bundle automatically at build time. No babel plugin or runtime loader needed.

## Risks & mitigations

- **Risk:** A missing env var crashes the app at module load with a hard throw, not a graceful fallback.
  - **Mitigation:** That's intentional. Falling back silently means a developer ships with the wrong config and discovers it in production. The throw includes the exact var name and a pointer to `mobile/.env.example`.

- **Risk:** Existing developer (i.e., Zeshan) needs to populate `mobile/.env` locally before the next `expo run:ios` or the app bricks at startup.
  - **Mitigation:** This branch's PR description includes the migration step. Additionally, `mobile/.env` is created on the developer's local filesystem during this implementation so the next run still works without manual setup.

- **Risk:** Future contributor clones the repo, runs the app, hits the throw, gets confused.
  - **Mitigation:** `mobile/.env.example` is committed with clear placeholder values. The throw message points at it. CLAUDE.md documents the setup.

- **Risk:** `EXPO_PUBLIC_*` vars are inlined into the JS bundle — they appear as plaintext strings in the production build. This is a *non-risk* for Firebase web config (designed-public) and the Cloud Run URL (designed-public), but worth noting for any future config that *is* truly secret.
  - **Mitigation:** Document in `mobile/.env.example` that anything in this file ends up in the bundle. Truly secret values must live on the backend, not in the mobile app.
