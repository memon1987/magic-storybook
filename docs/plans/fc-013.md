## Context

The current illustration pipeline produces page 1 first (no references), then generates pages 2..N in parallel with page 1's image as a single multimodal reference ([backend/src/services/gemini.ts:268-309](../../backend/src/services/gemini.ts#L268-L309)). It's a single-reference cascade.

Gemini 3.1 Flash Image (Nano Banana 2) documents support for **up to 4 character-consistency reference images per call** plus 10 object-fidelity references. We're at 25% utilization of the documented mechanism. Multi-reference is the model's primary lever for character consistency — underutilizing it leaves capability on the table.

Per the parent plan (`~/.claude/plans/lets-pick-back-up-warm-map.md`): user has decided that character consistency is product-paramount and is willing to spend the latency cost (~30-90s per story) for tighter consistency. **Magnitude of improvement is unmeasured** — could be subtle (~10%) or substantial (~50%). The goal is to fully use the model's documented mechanism, then measure post-deploy.

## Goals

- Generate one dedicated reference image per named character in `story.characterSheets` BEFORE generating any story pages
- Each character reference is a "model sheet": 3 poses (front, 3/4, action) on a clean white background, with the character's name labeled
- Every story page generation receives all character references as multimodal inputs (in addition to the existing page-1 setting reference)
- Surface the character reference URLs in the API response and persist them to Firestore so future regenerations or "About the characters" UIs can reuse them
- Backwards compatible: stories with empty `characterSheets[]` (e.g., LLM produced an empty array, or pre-FC-013 saved drafts) gracefully fall back to the existing page-1-only reference cascade

## Non-goals

- Generating multiple reference images per character. v1 = 1 image per character with 3 poses inside it.
- Caching character references across regenerations of the same story (deferred — would require hashing `characterSheets[]` and looking up cached URLs; future optimization).
- Surfacing the character reference images in the mobile app's library or reader UI. They're stored and served by the API but the mobile app doesn't render them in this FC.
- Per-character text descriptions in the illustration prompt are already in place ([illustration.ts:30-39](../../backend/src/prompts/illustration.ts#L30-L39)) — keep them; this FC adds the visual reference layer on top.

## Proposed approach

### New pipeline flow

```
[story text gen]                                 (~30-50s, unchanged)
    ↓
[generate 1 reference image PER character]       (~12-30s typical, parallel; new)
    ↓
[generate page 1 with all character refs]        (~12-30s, sequential; reference list grows)
    ↓
[generate pages 2..N in parallel
  with character refs + page 1 setting ref]      (~12-90s typical, multimodal payload grows)
```

### Backend file plan

**`backend/src/types/index.ts`:**

- Extend `GeneratedStory` and `StoryDocument` with `characterReferenceUrls?: Record<string, string>` (key = character name, value = Cloud Storage public URL)

**`backend/src/prompts/characterReference.ts` (new):**

- `buildCharacterReferencePrompt(name: string, description: string, style: ArtStyle): string`
- Returns a model-sheet prompt: clean white background; 3 poses arranged side-by-side (front view, 3/4 view, action pose); character's name labeled at the bottom; same `STYLE_DESCRIPTIONS` as the regular illustration prompt so the character matches the book's art style
- Explicitly NO scene context, NO other characters, NO text other than the name label. Forces the model to internalize the character's appearance

**`backend/src/services/gemini.ts`:**

- New `generateCharacterReference(character: CharacterVisualSheet, storyId: string, style: ArtStyle): Promise<{ name, publicUrl, imageBase64, mimeType }>`. Wraps the existing `generateContent` call + 503 retry pattern. Saves to Cloud Storage at `stories/{storyId}/character-refs/{name}-{uuid}.{ext}`.
- Rewrite `generateAllIllustrations` return type from `Promise<string[]>` to `Promise<{ pageUrls: string[]; characterReferenceUrls: Record<string, string> }>`. Backward-compatible at the route layer (route adapts).
- New flow:
  - If `story.characterSheets.length === 0`: fall through to legacy single-ref cascade (no character refs generated). Defensive — keeps the system working when the LLM produces an empty array.
  - Otherwise: parallel `Promise.all` over `story.characterSheets.map(generateCharacterReference)`. Collect a `Map<characterName, { base64, mimeType }>` for in-memory use during page generation, plus a `Record<characterName, publicUrl>` for the return value.
  - Generate page 1 with character refs (no setting ref since page 1 IS the setting establishing shot).
  - Generate pages 2..N in parallel; each call passes character refs + page 1 setting ref.

**`backend/src/prompts/illustration.ts`:**

- `buildIllustrationPrompt` signature gains `characterReferences?: Array<{ name: string }>` (just the names — image data is passed directly to `generateContent`, not into the prompt text). The prompt body references each character by name and reference index: "Character reference 1 shows ${name1} from front, three-quarter, and action poses. Character reference 2 shows ${name2}…"
- Page 1 setting reference text becomes "Setting reference (page 1)" (currently "the illustration from page 1") — clearer ordering

**`backend/src/services/gemini.ts` `generateIllustration` signature:**

- Replace single `referenceImageBase64?` arg with `references?: Array<{ name?: string; data: string; mimeType: string; type: 'character' | 'setting' }>`. Builds the multimodal `contents` array by iterating `references` in order: for each, push a `text` part naming what it is, then the `inlineData` part. Final part is the main prompt text.
- Backwards-compatible inside the module (caller is `generateAllIllustrations`, which is also being rewritten).

**`backend/src/routes/stories.ts`:**

- Adapt to the new `generateAllIllustrations` return shape. Persist `characterReferenceUrls` to the story Firestore doc alongside `pageCount`. Surface in the JSON response.

### Latency / cost trade — honest numbers

Per the parent plan:
- Currently observed (from `docs/investigations/fc-002-latency-benchmark-2026-04-28.md`): 68s / 145s / 435s for 4-page / 6-page / 8-page stories
- Add: 2-3 character refs in parallel as a sequential prefix (~30-60s typical, ~120s worst-case)
- Pages now have 1-3 extra multimodal inputs each (+1-3s per page)
- **Total typical 6-page story: 145s → 200-260s. Worst case still bounded by 600s Cloud Run timeout.**

Cost: +$0.03-0.05 per story (2-3 extra Flash image generations). Negligible.

User has explicitly accepted this trade.

## Critical files

- `backend/src/services/gemini.ts` — rewrite `generateAllIllustrations`; add `generateCharacterReference`; rework `generateIllustration` to accept ordered references
- `backend/src/prompts/illustration.ts` — multi-character-reference text in prompt; clearer setting-ref labeling
- `backend/src/prompts/characterReference.ts` (new) — dedicated model-sheet prompt builder
- `backend/src/types/index.ts` — extend `GeneratedStory` and `StoryDocument` with `characterReferenceUrls`
- `backend/src/routes/stories.ts` — adapt to new return shape; persist + serve character ref URLs

## Reuse

- 503 retry / placeholder fallback logic already in `generateIllustration` — `generateCharacterReference` shares the same model + same kind of failure mode
- `STYLE_DESCRIPTIONS` from `illustration.ts` — character refs should match the book's art style
- Cloud Storage upload helper inline in `generateIllustration` — extract to a small shared helper (or leave inline + duplicate; lean toward extract since now used by both functions)
- Existing `characterSheets[]` text descriptions in the illustration prompt — keep; visual references augment the text descriptions, don't replace them

## Risks & mitigations

- **Risk:** A character-ref generation hits the long-tail Nano Banana 2 latency (~250s observed in fc-002 benchmark). The entire pipeline stalls before any page generation begins.
  - **Mitigation:** Char refs run in parallel via `Promise.all`, so the worst single ref bounds the entire prefix (not the sum). With 2-3 chars, p50 should be ~30-45s, p95 ~120s. Worst case still under the 600s Cloud Run timeout because parallel.
  - If a single char ref fails outright (3 retries exhausted), `generateIllustration` returns a placeholder URL. We propagate the same fallback for `generateCharacterReference` — if a character ref fails, generate that page without that ref (degrade gracefully, log warn).

- **Risk:** Empty `characterSheets[]` from the LLM crashes the new pipeline.
  - **Mitigation:** Defensive fallthrough to legacy cascade when array is empty. No error to surface.

- **Risk:** Multi-image multimodal payload triggers Gemini's parallel quota issues at scale (already a known pain point per fc-002 investigation — 04-28's 8-page story had pages with 250s tail latency, suspected to be quota throttling).
  - **Mitigation:** This is a real risk. We're adding more multimodal calls to a system already stressing the quota. If post-deploy logs show worse tail-latency variance, the revert is one-PR rollback (delete this FC's commit; restore the single-ref cascade). The user has accepted this trade explicitly with the "we can roll just this one change back independently" framing.

- **Risk:** Character reference image quality is poor — model produces a low-quality 3-pose sheet that confuses rather than helps subsequent page generations.
  - **Mitigation:** Verification step generates 1-2 sample stories post-deploy and visually inspects the character refs. If they look bad, iterate `buildCharacterReferencePrompt` (add more constraints, examples) before claiming improvement. If iteration doesn't help, revert.

- **Risk:** `characterReferenceUrls` persisted to Firestore for new stories; older stories don't have it. Mixed library state.
  - **Mitigation:** The field is optional. Mobile clients ignore it (FC-013 doesn't surface refs in the UI). No regression for older stories; just a new field in the response.

- **Risk:** Illustration prompt now references characters by index ("Character reference 1 is X"). If the index numbers vs. names get desynced (e.g., refs reordered before the prompt builds), the prompt will lie to the model.
  - **Mitigation:** Build the references array and prompt text from the same iteration. Single source of truth — no separate index reordering step.

## Rollout

- Single feature branch: `feature/fc-013-character-references`
- Single PR (PR #7 expected)
