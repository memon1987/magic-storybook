## Context

Stories currently have no cover. The library's `StoryCard` uses `story.pages?.[0]?.imageUrl` as the thumbnail — which is whatever the first content page happens to look like (often an awkward in-medias-res scene). Compounding the issue, FC-013 just shipped per-character reference images; without a title page generated through the same multimodal pipeline, the cover (read: the user's first impression) wouldn't share the character renderings the rest of the book uses.

Per the parent overhaul plan (`~/.claude/plans/lets-pick-back-up-warm-map.md`): FC-012 is the third of four FCs in the storybook generation overhaul. Ships after FC-013 so the title page can use the canonical character references.

## Goals

- Generate a dedicated title-page image as part of every new story
- Title page is exposed via dedicated fields on the story (`titlePageImageUrl`, `titlePage: { text, sceneDescription }`) — NOT shoehorned into `pages[]` as a sentinel index
- Library `StoryCard` prefers `titlePageImageUrl`, falls back to `pages?.[0]?.imageUrl` (so older stories without a title page still get a thumbnail)
- Reader displays the title page first, then content pages, by composing its own render iteration locally
- Title page features the book's title text + a hero scene with the main characters in the book's signature setting
- Uses FC-013's character reference images as multimodal inputs so the cover characters look like the in-book characters
- Backwards-compatible: existing stories in the library (no `titlePage` / no `titlePageImageUrl`) continue to use their original `pages[0]` as the thumbnail and don't render an extra page in the reader

## Non-goals

- Putting the title page inside `pages[]`. **Plan deviation from the parent-plan v3 (which originally chose Option 1, sentinel `pageNumber: 0` in `pages[0]`).** Switched to a separate-field model (Option 2) for cleaner semantics — content pages keep their natural `pageNumber: 1..N` meaning, the title page is conceptually distinct (it's a cover, not a story page), and a future "regenerate cover only" or "About the cover" UI is straightforward. Marginal mobile cost: one line in StoryCard fallback, ~5 lines in Reader to prepend a virtual page-0 to its render array. Worth it for the data-model clarity.
- Animated covers, interactive covers, multiple cover variants. Single static image, same Nano Banana 2 model used for content pages.
- A retry-on-misspelling layer for the title text. Gemini handles short stylized text at ~90% accuracy; an occasional misspelled cover word is acceptable for v1. If user feedback says it's too noticeable, retry-on-misspell is a small follow-up FC.

## Proposed approach

### Story prompt (story.ts)

Schema gains a top-level `titlePage` object:

```json
{
  "title": "...",
  "titlePage": {
    "text": "On-cover display text. Usually the book title; may include 'Starring [child name]' as a smaller line if natural.",
    "sceneDescription": "Hero scene featuring the main characters in the book's setting. Composed for a book cover: characters central, evocative pose, signature setting elements. Will be used as a single image generation, NOT a multi-page sequence."
  },
  "characterSheets": [...],
  "settingIdentity": {...},
  "pages": [...]
}
```

Prompt instructions: write a hero scene that captures the spirit of the book without spoiling the ending. Title text is the primary on-image element; "Starring [childName]" is optional secondary text.

### New title-page prompt builder (`backend/src/prompts/titlePage.ts`)

Dedicated prompt builder analogous to `characterReference.ts` and the page `illustration.ts`. Inputs: `titlePage.text`, `titlePage.sceneDescription`, art style, character ref names (for the multimodal labels). Outputs a prompt that:
- Composes a hero scene per `sceneDescription`
- Renders the book's title text in playful display lettering, central composition, top or bottom of the image
- Uses the book's art style
- References the character ref images by name when applicable
- Specifies landscape aspect ratio (matches reader; user-decided in parent plan), with central subject so the library's 3:4 portrait crop shows the character cleanly

### Pipeline change (gemini.ts `generateAllIllustrations`)

```
[story text gen]
    ↓
[N character refs in parallel]                          (FC-013)
    ↓
[title page (with character refs as inputs)]            ← NEW
    ↓
[page 1 (with character refs as inputs)]
    ↓
[pages 2..N parallel (with character refs + page 1 setting ref)]
```

Title page generation runs sequentially after char refs but before page 1 so it can use the character refs as multimodal inputs. It does NOT use page 1 as a setting reference (page 1 doesn't exist yet at that point), but the `titlePage.sceneDescription` from the LLM is rich enough to stand on its own.

Return shape change: `pageUrls` becomes `[titlePageUrl, ...contentPageUrls]`. The route assembles the final pages array with `pageNumber: 0` for the title.

### Route persistence (routes/stories.ts)

When persisting to Firestore:
- **Story doc** gains two new top-level fields: `titlePageImageUrl: string` and `titlePage: { text: string, sceneDescription: string }`. Stored alongside the existing top-level fields like `title`, `pageCount`, etc.
- **Pages subcollection unchanged**: only content pages are stored as page docs with `pageNumber: 1..N`. The title page is NOT a page document — it's a story-level field.
- `pageCount` continues to count content pages only (preserves the user's "I picked 4 pages and got 4 content pages" mental model). The cover is implicit, like in any printed book.

Response payload mirrors the Firestore shape: top-level `titlePageImageUrl` + `titlePage` + a `pages[]` array containing only content pages.

### Mobile

- **`Story` type extension (`mobile/services/api.ts`):** add optional `titlePageImageUrl?: string` and `titlePage?: { text: string; sceneDescription: string }`.
- **Library (`mobile/components/StoryCard.tsx`):** thumbnail logic becomes `story.titlePageImageUrl ?? story.pages?.[0]?.imageUrl`. One-line change. Old stories (no titlePageImageUrl) still get a thumbnail.
- **Reader (`mobile/app/story/[id]/read.tsx`):** compose a local `renderPages` array that prepends a virtual title-page entry when `story.titlePageImageUrl` exists. The rest of the reader (page-curl, dots, page counter) iterates `renderPages` instead of `story.pages`. Page counter naturally reads "1 / N+1" for the title; optional polish: special-case index 0 to show "Cover".

### Latency / cost trade

- Title page generation = +1 sequential image gen (~12-30s typical, ~120s tail for Nano Banana 2 under contention).
- Character refs already generated by FC-013, so no incremental ref generation cost.
- Title page payload includes character refs (~3-4MB), similar to a content page.
- **Total story latency: FC-013 baseline + ~12-30s.** A 6-page story already at 200-260s post-FC-013 becomes ~215-290s with the title page.
- Cost: +$0.014 per story (one extra Nano Banana 2 image generation). Negligible.

## Risks & mitigations

- **Risk:** Title page misspells the book's title (Gemini ~90% on short stylized text). Cover with a misspelled title is embarrassing.
  - **Mitigation:** Accept for v1. If observed in practice, easy follow-up: generate the title image, OCR the rendered text, retry on mismatch (single follow-up FC, deferred until evidence).

- **Risk:** Adding another sequential stage to the pipeline pushes latency further. FC-013 already moved typical 6-page from ~145s to ~200-260s; FC-012 adds another 12-30s.
  - **Mitigation:** Same as FC-013 — explicit user trade. Rollback path is single-PR revert.

- **Risk:** `pageNumber: 0` sentinel for the title page conflicts with somewhere else in the codebase.
  - **Mitigation:** Verified by reading `read.tsx` and `StoryCard.tsx` — neither reads `pageNumber` directly for navigation; reader iterates by array index, library uses array index 0. Sentinel value is internal only.

- **Risk:** Library's 3:4 portrait crop on a landscape title page may decapitate the central character.
  - **Mitigation:** Title-page prompt explicitly composes for centered subject with safe-area headroom on both sides. If 3:4 crop still looks bad, future FC could generate a portrait variant or smart-crop server-side. Defer.

- **Risk:** Existing stories in the library don't have a title page — their `pages[0]` remains an in-medias-res content page. Mixed library state until users regenerate.
  - **Mitigation:** Acceptable. The visual diff is "old stories' covers look amateur compared to new ones," not "old stories are broken." Users can regenerate any story they want a proper cover for.
