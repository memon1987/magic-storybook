## Context

PR #26 (FC-017 Phase 2: resumable story-generation pipeline) was opened without the adversarial peer review CLAUDE.md requires for plan-driven L work. Two independent adversarial reviews were run after the fact:

- **Round 1** — distributed-systems / correctness lens via `/code-review max` (7 finder angles). Returned 15 ranked findings.
- **Round 2** — production-reliability / Firestore-semantics lens via a senior SRE persona, fresh context, no exposure to Round 1's findings. Returned 20 findings (some new, several confirming Round 1).

Both rounds converged on **REQUEST_CHANGES** and on the same six BLOCKER-class bugs that would cause production data corruption or stuck stories within the first month of real user traffic. Round 2 surfaced a 7th BLOCKER-tier bug (`FieldValue.serverTimestamp()` inside a nested map literal silently writing null) that Round 1 missed. The high inter-reviewer agreement validates both lists.

This plan consolidates the findings, ranks them, and sequences the remediation. Each fix is small and well-scoped; the plan's value is the prioritization, the verification contract, and the confirmation-review gate before PR #26 is allowed to merge.

**Sub-FC framing.** This is structurally a follow-up to FC-017 Phase 2 — not its replacement. PR #26's architecture is sound; the bugs are implementation-level. Sub-FC keeps the remediation work traceable + ensures the confirmation review per CLAUDE.md actually happens.

## Goals

- Ship every BLOCKER-class fix before PR #26 merges; nothing in PR #26 lands without these.
- Ship HIGH-class fixes either in the same PR or as documented follow-ups, with the deferral reasoning in writing.
- Document MEDIUM/LOW findings as either deferred (with FC entry) or accepted (with reasoning).
- Write the resume-logic test file (`backend/src/services/__tests__/resume.test.ts`) the FC-017 plan §211 explicitly named.
- Confirmation review per CLAUDE.md after fixes land; merge gated on CONFIRMED-CLEAN verdict.

## Non-goals

- **Architectural redesign** (Cloud Tasks vs same-process). Round 2 plan-critique flagged this; out of scope here. Worth a separate consideration before Phase 3 builds further on the lock+heartbeat machinery — file as FC-026 if you want to revisit.
- **Phase 3 (async 202-ACK / background worker) or Phase 4 (mobile snapshot / orphan sweep)**. Owned by FC-017 plan; this sub-FC does not touch them.
- **Re-running Phase 1 instrumentation work**. The 2026-06-22 stress-run + investigation note are still valid.

## Proposed approach

### Stage 1 — Six BLOCKERs (required pre-merge of PR #26)

Each fix is small; all six together are ~150 lines of focused changes plus tests. Group by file to minimize diff churn.

**B-1. Same-process lock re-entry race** (`backend/src/services/worker.ts:150`)

`claimLock` currently skips the lock-held guard when `data.workerId === WORKER_ID`. Two concurrent `runStoryWorker` calls on the same Cloud Run instance (concurrency=4 makes this trivial) both see their own WORKER_ID and both claim, then race on writes.

Fix: drop the self-skip; rely on the stale-heartbeat path for legitimate same-process re-entry. The lock is *strictly* released-then-reclaimed, never re-entered on the same WORKER_ID. Combined with an in-process `Map<storyId, Promise<RunStoryWorkerResult>>` to dedupe same-process concurrent calls before they hit the txn — second caller awaits the in-flight promise, not a new worker.

Verification: vitest that fires two `runStoryWorker(id)` calls in parallel within the same process. Exactly one wins; the other resolves to the same result via the promise cache (or returns LockHeldError, depending on semantics chosen — pick the former since it matches what the mobile double-tap actually wants).

**B-2. Placeholder URLs locked in on resume** (`backend/src/services/gemini.ts:1034, 1067`)

`savePage` is called with `ocrPassed: r.imageBase64 !== null`, but a generation-total-failure returns `{ publicUrl: 'https://placehold.co/...', imageBase64: null }`. The placeholder URL gets persisted; the resume skip filter checks only URL presence; the failure is locked in permanently.

Fix: don't write to `pageUrls` at all on `imageBase64 === null` — that signals a complete generation failure, not an OCR miss. Let the resume regenerate it. Update both the anchor-page and parallel-page savePage call sites.

Verification: vitest that simulates a placeholder return from generateIllustration and asserts savePage is NOT called for that page; the page is regenerated on the next runStoryWorker invocation.

**B-3. Heartbeat race with batch.commit and finally** (`backend/src/services/worker.ts:199, 314`)

Two related races: (a) an in-flight heartbeat update can land AFTER `batch.commit()` deletes workerHeartbeatAt, resurrecting the field on a completed doc; (b) the `finally` block clears workerId/workerHeartbeatAt unconditionally, including in the take-over scenario where a successor worker has already claimed the lock.

Fix: stop the heartbeat BEFORE the terminal `batch.commit()` (move `clearInterval` to the success path, await any in-flight refresh promise). Make the `finally` lock-clear transactional + conditional on `workerId === WORKER_ID` — only clear if we still hold the lock. Add `heartbeat.unref()` so the interval doesn't prevent Node process exit.

Verification: integration test (manual or scripted) — kill the worker process mid-flight, confirm finally doesn't run; assert a future /resume can claim the lock after 90s.

**B-4. `FieldValue.serverTimestamp()` inside nested progress map writes null** (`backend/src/services/worker.ts:118`)

The Firestore Admin SDK only guarantees sentinel-value resolution at the top level of an update or via dot-notation. Nested sentinels in object literals may silently serialize as null. Phase 4's orphan-sweep design depends on `progress.updatedAt` being a real server timestamp; today it's not.

Fix: rewrite `saveProgress` to use per-key dot-notation:
```ts
await this.storyRef.update({
  'progress.phase': phase,
  'progress.completedSteps': completedSteps,
  'progress.totalSteps': totalSteps,
  'progress.message': message,
  'progress.updatedAt': FieldValue.serverTimestamp(),
});
```

Verification: integration smoke — call saveProgress, read the doc back, assert `progress.updatedAt` is a Firestore Timestamp (not null, not the sentinel-object literal).

**B-5. Catch-vs-finally lock window leaves doc permanently stranded** (`backend/src/services/worker.ts:296, 314`)

If the catch's `storyRef.update({ status: 'failed', failureReason })` succeeds but the `finally`'s lock-clear update fails (transient Firestore unavailability between the two awaits), the doc is permanently `status: 'failed'` with `workerId` set and a fresh-ish workerHeartbeatAt. Next /resume sees LockHeldError → 409. Story is un-resumable until the 90s staleness window passes.

Fix: collapse the catch's status-failed write and the lock-clear into a single atomic update. The `finally` becomes pure cleanup (clearInterval + best-effort lock-clear only if we still hold it per B-3).

Verification: covered by B-3's vitest (same code path).

**B-6. Resume null-as-failure infinite retry** (`backend/src/services/gemini.ts:937, 938`)

`castAlreadyDone = !!state.castReferenceUrl` and `titleAlreadyDone = !!state.titlePageImageUrl` — if a prior run persisted `null` to record failure (per `worker.ts:103-106`'s explicit intent), the `!!` check returns false and the generation re-fires on every resume.

Fix: distinguish "never attempted" from "attempted and failed". Two options:
- (a) Add `castAttempted` / `titleAttempted` boolean fields and gate on those.
- (b) Persist a sentinel string ('FAILED') rather than null. The skip check becomes `state.castReferenceUrl !== undefined`.

Recommend (a) for clarity. JobState gets two new optional fields; FirestoreJobStateWriter writes them.

Verification: vitest — saveCastReference(null) sets castAttempted=true; subsequent resume's castTodo computation returns false; generateCastReference is not called.

### Stage 2 — Eight HIGHs (required pre-merge OR documented deferral)

Group into 4 themed batches; each can land as a small commit or sub-PR within feature/fc-017-resumable-pipeline.

**H-Group A: Privacy / data leak** (gate: must ship pre-merge)

- **H-1 Sanitize `failureReason`** (`worker.ts:298`): whitelist enum (`generation_error`, `network_error`, `quota_exceeded`, `safety_blocked`, `unknown`); raw `err.message` goes to server logs only, never to Firestore.
- **H-2 Field allowlist on GET /:id** (`stories.ts:288`): explicitly construct the response object instead of `res.json({ id, ...storyData, ... })`. Whitelist: title, childName, childGender, favoriteAnimal, setting, moral, artStyle, writingStyle, pageCount, status, characterReferenceUrls, titlePageImageUrl, progress (if mid-flight), failureReason (sanitized), pages. Explicitly exclude: workerId, workerHeartbeatAt, storyText, pageUrls, attempt.

**H-Group B: Lock correctness** (gate: must ship pre-merge)

- **H-3 Clock-skew guard on lock staleness** (`worker.ts:152`): treat negative `ageMs` as fresh (worker clock ahead of Firestore) rather than falling through to take-over. Add a `Math.max(0, ageMs)` or explicit `if (ageMs < 0) treat as not-stale`.
- **H-4 Non-null assertion safety** (`worker.ts:208`): replace `docData.childName!`, `docData.setting!`, etc. with explicit checks that throw `StoryNotResumableError` if any required field is missing. Fail loudly, not silently.

**H-Group C: Telemetry restoration** (gate: should ship pre-merge; if not, file a follow-up FC)

- **H-5 `resumed` flag accuracy** (`worker.ts:73, 285`): emit `resumed: state.attempt >= 1` (the doc's pre-claimLock attempt counter is 0 only on first run; ≥1 means resume).
- **H-6 Pre-claim failure observability** (`worker.ts:197`): wrap `claimLock` in the same try/catch that wraps the rest of the worker, OR emit a `total` failure stage_event from the route's catch on LockHeldError/StoryNotResumableError/transient Firestore errors.
- **H-7 Restore `firestore_persist` stage event** (`worker.ts:279`): bracket the `batch.commit()` with a timer + `emitStageEvent({ stage: 'firestore_persist', ... })`. FC-016 dashboards depend on this signal.
- **H-8 Per-page `saveProgress` in parallel batch** (`gemini.ts:1067`): add `await writer.saveProgress('parallel-pages', completedCount + 1, totalSteps, progressMessage(...))` inside the `mapWithConcurrency` callback (with an atomic completedCount counter). Mobile reader sees real progress instead of a frozen bar.

**H-Group D: Operational** (gate: should ship pre-merge)

- **H-9 Char name dot-escape** (`worker.ts:99`): wrap the dot-notation update with `FieldPath`: `this.storyRef.update(new FieldPath('characterReferenceUrls', name), url)`. Firestore treats FieldPath args as literal keys; embedded dots in `name` no longer create nested maps. Same for `pageUrls.N` in `savePage` (string-keyed; safer to use FieldPath).
- **H-10 Heartbeat `.unref()` + SIGTERM handler** (`worker.ts:199`): `heartbeat.unref()` after construction. Register `process.on('SIGTERM', ...)` to clear active heartbeats + write `status: 'failed', failureReason: 'sigterm'` for any in-flight stories, so Cloud Run scale-down doesn't leave zombie locks.

### Stage 3 — Six MEDIUMs (defer with rationale, OR opportunistic)

- **M-1 saveProgress quota cost** (~21 Firestore writes per story): debounce or batch (e.g. write only on phase boundary changes + every N items within a phase). Defer; revisit when concurrent-user count exceeds 10/sec.
- **M-2 attempt overcounting on tx retry** (`worker.ts:159`): minor; tx retries on contention are rare. Defer.
- **M-3 Worker doesn't re-verify userId**: defense-in-depth; route is the only caller today. Defer with comment in worker.ts header documenting the assumption.
- **M-4 Double-write lock-clear on success path**: cleaned up as part of B-3 (move lock-clear into the success batch; finally becomes best-effort). No separate work.
- **M-5 `'pending'` → `'queued'` migration**: backfill any stuck `status: 'pending'` Firestore docs to `status: 'failed', failureReason: 'pending-zombie-from-pre-FC-017'`. One-time gcloud script. Defer to a maintenance window.
- **M-6 storyText 1MB risk in parent doc**: move to a sub-document `stories/{id}/private/storyText` only if doc size becomes a concern. Defer; monitor doc size in production.
- **M-7 `new Firestore()` per call leaks gRPC pools**: hoist to module-level `const db = new Firestore()`. **Ship pre-merge** — trivial fix + compounds the OOM hypothesis the Phase 1 investigation flagged.

### Stage 4 — Six LOWs (document, accept, or defer)

- **L-1 STORAGE_BUCKET silent failure** (`gcsDownload.ts:15`): replace `!` with an explicit `throw new Error(...)` at module load. Pre-merge fix; one line.
- **L-2 uuid 32-bit collision space**: use full UUID. Pre-merge; one line.
- **L-3 progressMessage off-by-one** (`jobState.ts:108`): align the with-charName and without-charName branches on the same counter semantic. Pre-merge; trivial.
- **L-4 pageUrls cast on corrupted doc** (`worker.ts:80`): add runtime guard; defer.
- **L-5 noopWriter masks production misuse** (`gemini.ts:769`): remove the default-fallback; force callers to pass a writer. Pre-merge; tests pass an explicit noop.
- **L-6 stage-message rendering on backend**: noted but accepted; backend-rendered progress copy is a reasonable design call. No fix.

### Stage 5 — Test coverage (required pre-merge per CLAUDE.md + plan §211)

Create `backend/src/services/__tests__/resume.test.ts` with at minimum:
- JobState with partial `characterReferenceUrls` → skip those, generate the rest (mock generateCharacterReference, assert call set).
- JobState with `castReferenceUrl` present → skip cast generation.
- JobState with all `pageUrls[N]` present + `ocrPassed: true` → no page generation.
- JobState with placeholder URL in pageUrls → DOES regenerate (verifies B-2 fix).
- claimLock transaction: concurrent same-process calls serialize to one winner (verifies B-1 fix).
- claimLock with stale heartbeat (>90s old): new worker can take over.
- claimLock with fresh heartbeat: throws LockHeldError.
- Worker that throws mid-flight + finally release: lock is correctly released; future resume can claim (verifies B-5 fix).
- saveProgress: writes are observable via `progress.updatedAt` as a real Firestore Timestamp (integration test, verifies B-4 fix).

Aim for ≥80% coverage of worker.ts and the resume branches of generateAllIllustrations. Mocks acceptable; integration tests for the Firestore-semantics-dependent cases (B-4 verification).

## Risks & mitigations

- **Fix-introduced regressions.** Each remediation is small but the cumulative diff against PR #26 is substantial (~250-400 lines). *Mitigation:* Stage 6 confirmation review with explicit STILL-BROKEN / NEW-REGRESSIONS sections.
- **Test coverage gap detected.** Stage 5's resume.test.ts is new ground; mocking the Firestore Admin SDK + Cloud Storage + Gemini SDK for resume scenarios isn't trivial. *Mitigation:* favor injecting test-double JobStateWriter + mocking generateCharacterReference / generateIllustration at the function level rather than at the SDK level. Existing `instrumentation.test.ts` shows the pattern.
- **Scope creep into HIGHs/MEDIUMs.** Tempting to fix everything in one PR; result is a huge diff. *Mitigation:* enforce the Stage 1-5 sequence; HIGHs ship with BLOCKERs in PR #26; MEDIUMs defer to a follow-up PR with a clearly-scoped commit list.
- **The B-1 in-process dedup Map (Map\<storyId, Promise\>) introduces a new concurrency primitive.** Forgetting to clear entries on completion leaks promises. *Mitigation:* `try/finally` around the entry-add/remove; vitest that asserts the Map is empty after a run completes.
