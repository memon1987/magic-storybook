## Context

Sub-FC of FC-017. The mobile state-machine reviewer (R2) in the 2026-06-23 system-level retrospective ([docs/investigations/fc-017-retrospective-2026-06-23.md](../investigations/fc-017-retrospective-2026-06-23.md)) found 4 HIGH-severity defects in the FC-017 Phase 4 mobile client, including one that **directly contradicts the FC-017 plan's user promise**: the library tab shows stale generating-status forever because it has no Firestore subscription or `refetchInterval`. The plan said "feel free to come back later — we'll have it ready in your library." The library is the surface the user comes back to. It doesn't update.

The incident-closure reviewer (R4) independently surfaced two of the same residuals (R-1 5-15 min stuck-spinning window + R-2 no auto-resume) as ways the original 2026-05-12 user-visible failure can still recur.

This plan closes the mobile-side residuals without touching the backend contract.

## Goals

- Library tab live-updates while a story is mid-generation (R2 HIGH-1 + R4 R-6).
- Fix `navigatedRef` post-Resume stuck-state on `/generating` (R2 MEDIUM-2).
- Add a client-side watchdog: if `progress.updatedAt` hasn't advanced in 90s, surface a soft "this may be stuck" UI before the sweep formally flips the doc (R2 HIGH-3 + R4 R-1).
- `permission_denied` recoverable via force-token-refresh + re-subscribe instead of unrecoverable until app-restart (R2 HIGH-2).
- Auth-readiness gate on `/generating` to prevent the deep-link race (R2 HIGH-4).
- Retry budget: mobile reads `attempt` and caps Resume at 3 attempts; surface "try different inputs" copy for `safety_blocked` (R2 state-machine gap + R4 R-2 + R4 R-4).

## Non-goals

- Backend changes (those are FC-030 corruption hotfix + FC-032 ops floor).
- Push notifications when a story completes (R4 R-9 — explicitly out-of-scope per FC-017 plan).
- React Query → full Firestore-driven cache (out of scope; `refetchInterval` is sufficient for this round).
- Reader screen defensive gate (R2 MEDIUM-1) — minor; defer to a separate FC.

## Proposed approach

### Change 1 — Library live-update via `refetchInterval`

[mobile/app/(tabs)/index.tsx:35-38](../../mobile/app/(tabs)/index.tsx#L35-L38):

```diff
const { data: stories, isLoading, refetch, isFetching } = useQuery({
   queryKey: ['stories'],
   queryFn: () => listStories(),
+  // While any non-terminal row exists, poll every 15s so the library
+  // reflects live generation state. React Native has no window-focus
+  // signal, so staleTime alone never auto-refetches. 15s ≈ heartbeat
+  // cadence — costs ~4 list-fetches/min × 1 user on this screen.
+  refetchInterval: (q) => {
+    const rows = q.state.data ?? [];
+    const anyInFlight = rows.some(
+      (s) => s.status === 'queued' || s.status === 'generating'
+    );
+    return anyInFlight ? 15_000 : false;
+  },
});
```

15s cadence matches the worker heartbeat (no point polling faster than the writes happen). When all rows are terminal (`complete` or `failed`), polling stops. Cost: ~4 list-fetches/min while the user is on the library screen with anything in-flight. Backend list-fetch is light (one indexed query, ≤100 docs).

Cheaper alternative considered + rejected: a collection-level Firestore subscription. More efficient at scale, but adds complexity (subscription teardown on navigation, React Query cache patching) for a single-user app at current scale. Ship `refetchInterval`; revisit if cost becomes real.

### Change 2 — `navigatedRef` stuck-state fix

[mobile/app/story/[id]/generating.tsx:52-65](../../mobile/app/story/[id]/generating.tsx#L52-L65):

The current `navigatedRef.current` is a plain boolean reset only on `useEffect` remount (id change). After a Resume cycle that flows `generating → failed → Resume → complete` on the same screen instance, `navigatedRef.current` is already `true` from the first nav attempt → the `'complete'` snapshot never triggers `router.replace` → user is stuck on `/generating` showing "Starting…" forever on a completed story.

Fix: drop the `navigatedRef` entirely. `router.replace` is idempotent on identical-href calls in Expo Router (it no-ops if the current route already matches the target). The ref was added defensively against a concern (re-firing on a different screen) that doesn't apply because `useEffect` cleanup tears down the subscription on unmount, and the closure is GC'd with the screen.

If `router.replace` idempotency proves not to hold under some Expo Router edge case, the fallback is making `navigatedRef` track `(id, attempt)` tuples and resetting it whenever `result.attempt` advances — but verify the simpler fix first.

### Change 3 — Client-side watchdog

[mobile/app/story/[id]/generating.tsx](../../mobile/app/story/[id]/generating.tsx):

Add a `useEffect` that records `progress.updatedAt` whenever it advances, plus a `setTimeout` that fires 90s after the last advance and surfaces a soft "Looks slow — try again?" UI with an early Resume button. Without this, on a hard instance death (no SIGTERM) the user sees "Generating page 3 of 6…" + spinner for the full 5-15 min until the sweep flips the doc.

Pair with a backend change: the route's initial `set()` should populate `progress` synchronously so the very first snapshot mobile sees has `progress.message='Starting…'` + `updatedAt=now`, eliminating the silent-queued window. Add to `routes/stories.ts:186-202` (FC-031, this PR):

```typescript
await storyRef.set({
  // ... existing fields ...
  progress: {
    phase: 'story-text',
    completedSteps: 0,
    totalSteps: 1,
    message: 'Starting…',
    updatedAt: FieldValue.serverTimestamp(),
  },
  // ... rest ...
});
```

This is the only backend change in this FC — small enough to belong here rather than in FC-030.

### Change 4 — `permission_denied` recovery

[mobile/services/stories.ts:72-80](../../mobile/services/stories.ts#L72-L80) + the screen's render of the `permission_denied` state:

On `permission_denied`, surface a "Try again" button that:
1. Calls `auth.currentUser.getIdToken(true)` to force a fresh token.
2. Tears down the existing subscription.
3. Calls `subscribeToStory` again with the refreshed token.

Most `permission_denied` events in production are token-expiry-related; force-refresh closes them.

### Change 5 — Auth-readiness gate

[mobile/app/story/[id]/generating.tsx](../../mobile/app/story/[id]/generating.tsx):

Add `const { user, loading } = useAuth();` at the top. Render a spinner (or short-circuit to `/login`) while `loading || !user`. The Firestore subscription only fires after auth is hydrated.

### Change 6 — Retry budget + safety-blocked UX

Two parts:

**(a) Read `attempt` on mobile.** Expand `CLIENT_VISIBLE_DOC_FIELDS` allowlist ([backend/src/routes/stories.ts:24-30](../../backend/src/routes/stories.ts#L24-L30)) to include `attempt`. Mobile types: add `attempt?: number` to `StorySnapshot`.

Wait — `attempt` was originally excluded because it's an internal counter. Reviewer R2 argued for client visibility; this is correct because the mobile needs to render "Tried 3 times" UX. Add to the allowlist with the test asserting it's now allowed.

**(b) Mobile copy + Resume gating.** In `generating.tsx`'s failure branch:
- If `failureReason === 'safety_blocked'`: suppress Resume; show "Create a new story" CTA that routes to `/create`.
- If `attempt >= 3`: suppress Resume; show "Tried a few times — try different inputs" + "Create a new story" CTA.
- Otherwise: Resume as today.

This closes the cost-loop residual (R4 R-4 — user burning ~$0.50-$1.10/Resume in a tight retry loop).

## Risks & mitigations

- **Risk: `refetchInterval` at 15s drains battery on the library tab.** Polls only when non-terminal rows exist; typical user has 0-1 in-flight stories. Cost is bounded.
- **Risk: dropping `navigatedRef` re-introduces the original double-route bug.** `router.replace` is documented idempotent. If we hit the edge case, the `(id, attempt)` tuple fallback closes it.
- **Risk: exposing `attempt` to mobile leaks worker internals.** It's a single counter; not a privacy concern. Add to allowlist + update test.
- **Risk: forcing token refresh on every `permission_denied` thunders the auth service if the rule denial is legitimate.** Add a circuit-breaker: at most one refresh attempt per minute.
