## Context

Today `POST /api/stories/generate` is a single synchronous HTTP request that runs for 3–5 minutes through the FC-013/FC-012/FC-020 pipeline. Two production failure modes are well-documented:

1. **Hard instance loss (observed 2026-05-12).** ~9.5 min in, with story text + 1 of 2 char refs + title page already produced and page 1 mid-flight, the Cloud Run instance died (cascading from a `TypeError: fetch failed sending request` on a char-ref call to Gemini). No new instance picked the work up. ~80% of the spend was thrown away and the user saw a generic timeout.
2. **Silent-success on client timeout (measured in FC-020's 8-page run, 2026-05-24).** Wall-clock was **440 s**, of which the **char-ref stage was ~332 s** (one ref hit a 503 and took ~331 s) and the page stage was only ~62 s. The mobile axios timeout is **600 s** (`mobile/services/api.ts`); Cloud Run is **3600 s** (set via `--timeout=3600` on `gcloud run deploy`, not in a checked-in `cloudbuild.yaml`). When the client fires its timeout the backend keeps running, finishes, saves the story to Firestore, and the user sees a hard error — then the story silently appears in the library on next refresh. Worst possible UX for an otherwise-successful generation.

Any 3–5 min synchronous request is structurally fragile under autoscaling, instance restarts, network blips, and Cloud Run cold-eviction. The FC entry calls out the explicit risk: we don't yet know whether instances die from **OOM** (multimodal image payloads are 600 KB+ each, char refs run in parallel, refs accumulate as `imageBase64` for downstream prompts), **connection-pool exhaustion** (Gemini calls with no explicit pooling, char-ref retries can stick), or **Cloud Run scale-down kills**. Picking an architecture without that data risks solving the wrong layer.

This plan is structured around that risk. **Phase 1 is investigation** — we measure before we refactor. **Phase 2** makes the pipeline resumable so the next instance death doesn't throw away 80% of the work. **Phase 3** moves the request itself to an async job model so the client-timeout class of bug disappears entirely. **Phase 4** wires the UX. The **silent-success bug** is patched as soon as Phase 2's job-state Firestore doc exists, ahead of the full async refactor — it's the most user-visible symptom and shouldn't wait.

## Coordination with FC-016 (latency)

FC-016 and FC-017 are designed to run **in parallel** — different layers, different goals (FC-016 reduces call-level latency; FC-017 buys orchestration-level durability). Same files get touched (`gemini.ts`, `stories.ts`, `textVerify.ts`) but at different sites; no architectural coupling.

Two practical coordination points:

1. **Share Phase 1 instrumentation.** This plan's Phase 1 (per-phase memory + timing + Gemini call wrapper + request-tagged logs) and FC-016's Phase 1 (per-stage structured JSON logs) overlap substantially. Land them as **one shared instrumentation PR** that satisfies both Phase 1 exit criteria at once. Avoids two near-identical logging refactors stepping on each other.
2. **Land this plan's Phase 2 before FC-016's cache lever (A1).** The FC-016 cache lookup naturally lives at the same Firestore-aware boundary this plan introduces in Phase 2 (per-char-ref persistence). Doing Phase 2 first saves a small refactor for FC-016. Not a hard blocker — reversed order works, just adds ~½ day of weaving. After both Phase 2s, the remainder (FC-016 cache/fewer-refs, this plan's Phase 3 async + Phase 4 silent-success fix) is fully parallel.

FC-016's E1 lever (per-call 60s timeout) is independent of this plan and can ship at any point.

## Goals

- Root-cause the 2026-05-12 instance death with **evidence, not guesses**, and pick the architectural fix that addresses the actual failure layer.
- Persist intermediate artifacts (story text, char ref URLs, cast ref URL, title page URL, completed page URLs, OCR scores) to Firestore at every phase boundary, so a resumed worker generates only what is missing.
- Move story generation to an async job model: mobile POSTs → gets `{ jobId, storyId }` immediately → subscribes to the Firestore story doc for live progress → never holds a 3–5 min HTTP connection again.
- **Fix the silent-success bug** ahead of the full async refactor so it stops shipping to real users today.
- Surface real progress in the UI ("Generating page 3 of 6…") and an orphan-sweep that marks stuck Firestore docs as `failed` so the library never shows a zombie "generating" row.

## Non-goals

- **Reducing total generation latency.** That's FC-016 (char-ref bottleneck). This plan makes the pipeline durable; it does not make it faster.
- **Changing the image/text models, prompts, OCR-verify thresholds, or the FC-020 baked-text pipeline.** Same generation logic; new orchestration around it.
- **Cloud Run `min-instances=1`.** Worth its own decision when usage justifies $15/mo; out of scope here.
- **Back-filling old failed/zombie stories.** The orphan-sweep covers from deploy forward; pre-existing zombies are cleared manually.
- **A separate worker service (Cloud Functions, Cloud Tasks → Cloud Run).** Phase 3 recommends staying on the existing Cloud Run service with a background-job pattern (reasoning below); if Phase 1 finds OOM/scaledown evidence that contradicts this, the recommendation gets reopened — not this plan's scope to pre-litigate.

## Proposed approach

### Phase 1 — Investigation (gating)

**Exit criterion:** before Phase 2 lands, we have ≥ 3 production generation runs instrumented end-to-end (including ≥ 1 deliberately stressed run of a 12-page story), and we can name *which* of OOM / connection-pool / scaledown / Gemini-side fault was the cause of the 2026-05-12 death (or rule them all out and broaden the search).

What to add — small, non-behavioral instrumentation, shippable as a separate prep PR ahead of the architecture work:

1. **Per-phase timing + memory snapshots in `generateAllIllustrations`** (`backend/src/services/gemini.ts`). Log structured JSON (`{ phase, storyId, elapsedMs, rss, heapUsed, externalBytes }`) at each phase boundary: after story text, after each char ref completes (currently logged only as count), after cast + title, after each canonical-anchor page, after the parallel batch. Use `process.memoryUsage()` — zero-cost; we already do nothing with the values. Lets us see whether RSS climbs monotonically across char refs (smoking gun for OOM via accumulated `imageBase64` buffers — they're ~600 KB+ each and the FC-020 cap is `MAX_CHARACTER_REFS = 10`, so worst case ~6 MB resident from refs alone, plus their use as multimodal inputs).
2. **Request-scoped log tag.** Every log line in the generation path prefixes `[story:${storyId}]`. Today an instance death loses *which* request it was handling — this fixes it. Implement via a `child` logger pattern or a simple `console.log` wrapper threaded through the call.
3. **Cloud Run metrics to chart for each run.** No code change — just the Cloud Console queries to capture in the investigation note:
   - `run.googleapis.com/container/memory/utilizations` (instance memory %)
   - `run.googleapis.com/container/instance_count` (did we scale down mid-request?)
   - `run.googleapis.com/container/cpu/utilizations`
   - Container restart count over the run window.
4. **Gemini call wrapper that records outcomes.** Wrap `ai.models.generateContent` calls in the four generation functions (`generateStory`, `generateIllustration`, `generateCharacterReference`, `generateCastReference`, `generateTitlePage`) to log `{ kind, attempt, statusCode, errorClass, elapsedMs }` on every call (success or failure). Today we log retries but lose what specifically failed and how long the failed call took before throwing. This is how we tell `fetch failed` (network reset) from a 503 (Gemini overload) from a 500 (Gemini internal) — they each imply different fixes.
5. **A deliberately-stressed 12-page run.** FC-020's measured 440 s on 8 pages had `length=long` producing 8 pages. Force a real 12-page story (multiple named characters, hits the `MAX_CHARACTER_REFS` cap path) and capture the memory trace + Cloud Run metrics. This is the closest reproducer of the 2026-05-12 death we can manufacture without waiting for it to happen organically.

Write findings to `docs/investigations/fc-017-instance-death-${date}.md`. Promote to Phase 2 once we can point at a root cause.

**Why this is Phase 1 and not "do it later":** the FC explicitly calls this out: *"Without knowing whether instances die from OOM vs network vs scaledown, we'd be solving the wrong layer."* An async job model on a worker that still OOMs is a strictly worse failure (now the worker silently dies *and* there's no HTTP connection to surface the failure). The resume logic in Phase 2 must know what it's resuming *from* — if instances die from OOM mid-char-ref-batch, the resume protocol needs char-ref-level granularity, not "the whole char-ref stage finished or didn't."

### Phase 2 — Make the pipeline resumable

The pivot: today the only persistence during generation is the initial `status: 'generating'` write in `backend/src/routes/stories.ts:93` and the final `batch.commit()` at the end. Everything in between lives in-process. A crashed instance loses everything.

New model: **the Firestore story doc is the job state**. Every phase boundary writes its output to the doc the instant it produces something durable (a Cloud Storage URL). A resumed worker reads the doc, sees what's already done, and skips ahead.

1. **Extend the story doc schema** (`backend/src/types/index.ts`, persisted by `backend/src/routes/stories.ts`):
   ```
   status: 'queued' | 'generating' | 'complete' | 'failed'
   progress: {
     phase: 'story-text' | 'char-refs' | 'cast' | 'title' | 'anchor-pages' | 'parallel-pages' | 'finalizing'
     completedSteps: number
     totalSteps: number          // e.g. char refs done / total, pages done / total
     message: string              // human-readable, e.g. "Generating page 3 of 6"
     updatedAt: Timestamp
   }
   // Intermediate artifacts (the resume payload):
   storyText?: GeneratedStory     // full text + character sheets, persisted right after Step 1
   characterReferenceUrls?: Record<string, string>  // already persisted at end; now persisted incrementally
   castReferenceUrl?: string
   titlePageImageUrl?: string
   pageUrls?: Record<number, { url: string, ocrPassed: boolean, attempts: number }>  // per page
   workerId?: string              // Cloud Run revision + instance ID currently holding the job
   workerHeartbeatAt?: Timestamp  // updated every ~15s while the worker is alive
   attempt: number                // resume attempt counter (1, 2, ...)
   failureReason?: string         // populated on terminal failure
   ```

2. **Refactor `generateAllIllustrations`** to be **resume-aware**. Today it takes `(story, storyId, ...)` and produces everything from scratch. New signature accepts a `JobState` object containing what's already done and returns the same shape. Concretely (`backend/src/services/gemini.ts`):
   - Before generating char refs, read existing `characterReferenceUrls`; skip names that already have a URL. The function that loads a saved ref re-downloads the bytes from Cloud Storage so they can still be used as multimodal inputs to downstream page calls. (Cloud Storage GET on a 600 KB image: ~50 ms — negligible vs the ~5–30 s a char ref generation costs.)
   - Before generating cast: if `castReferenceUrl` is set, re-download bytes; skip generation.
   - Before generating title: if `titlePageImageUrl` is set, skip.
   - Before each page: if `pageUrls[pageNumber]` exists and `ocrPassed === true`, skip. **Skip even on `ocrPassed === false`** — we already accepted a best-F1 candidate per FC-020's policy; resuming should not regenerate pages that the previous run consciously kept.
   - The canonical-anchor pages (first K) must be regenerated *and re-uploaded* if they're missing, because downstream parallel pages need them as multimodal anchors. If they're present, re-download their bytes as anchors and skip generation. This is the key correctness invariant of the resume — anchors must be in-memory for the parallel batch even when not re-generated.

3. **Phase-boundary writes.** Each `await` that produces a durable artifact is immediately followed by a Firestore update of just the new field plus `progress`. Concretely:
   - After `generateStory()`: write `storyText`, `progress = { phase: 'char-refs', completedSteps: 0, totalSteps: chars.length }`.
   - Inside the char-ref `Promise.all`, replace it with a wrapper that, on each individual ref success, does a partial doc update merging in `characterReferenceUrls[name] = url` and incrementing `progress.completedSteps`. (Use `FieldValue.increment(1)` for the counter; merge for the URL map.) This is the highest-leverage resume granularity — char refs are the longest stage (332 s in the measured run) and the place an instance is most likely to die. Per-ref persistence means a death after 7 of 10 refs only redoes 3 refs on resume.
   - After cast + title (`Promise.all`): two-field merge update.
   - After each sequential anchor page: merge `pageUrls[pageNumber]` + bump progress.
   - After the parallel batch (or, ideally, after each page in the batch via the same `mapWithConcurrency` wrapper pattern as char refs): merge each result as it lands.
   - Final batch commit: status → `'complete'`, clear `workerHeartbeatAt`.

4. **`progress.message` formatting** lives next to the writes, not in a UI helper — backend renders the user-facing string ("Generating character: Mira", "Generating page 3 of 6", "Verifying text on page 2") so the mobile reader is a dumb subscriber.

5. **Worker heartbeat.** A `setInterval(15_000)` per in-flight job writes `workerHeartbeatAt = serverTimestamp()`. Cleared on terminal success/failure. This is what the orphan sweep (Phase 4) uses to detect stuck jobs.

6. **Crash safety for partial writes.** All updates use `merge: true` and `FieldValue` operations so a partial write never corrupts the doc. No transactions needed — there's a single writer per job (the worker holding `workerId`).

**Why char refs are explicitly the highest-leverage stage:** FC-020's measured run pinned the char-ref stage at ~332 s of 440 s wall-clock (75%). If the instance dies, it almost certainly dies during char refs. Per-char-ref persistence is the difference between "lose 75% of the work" and "lose at most one char ref."

### Phase 3 — Async job model

**Recommendation: keep the worker on the same Cloud Run service, using a background-task pattern with a synchronous-ish ACK.** Concretely:

- `POST /api/stories/generate` does the input validation, writes the initial Firestore doc (`status: 'queued'`), kicks off generation as a *fire-and-forget* async function (no `await`), and **immediately returns `{ jobId, storyId }`** with HTTP 202 Accepted.
- The background function runs the same `generateAllIllustrations` (now resume-aware), writing progress to Firestore as it goes.
- The mobile client subscribes to the Firestore story doc via `onSnapshot` and renders progress live.

**Why this instead of Cloud Tasks → Cloud Run / Cloud Functions / a separate worker service:**

1. **Cloud Run already runs requests past the response.** A response sent with `res.json(...)` does not terminate the JS event loop; the request handler can keep doing work as long as the instance is alive. This is exactly the silent-success behavior we observe today — Cloud Run lets the backend run to 3600 s even after the client gave up. We're going to *use* that behavior intentionally instead of leaking it. (Caveat: Cloud Run's CPU is throttled to near-zero between requests when "CPU allocation: request" is set. We must verify the service is set to **"CPU always allocated"** for the duration of background work — if not, change it as part of this plan. This is one knob on the Cloud Run service config, not a new service.)
2. **Cloud Tasks adds a queue, retry policy, dead-letter, and a second HTTP hop with auth.** We don't need any of that yet — we have at most ~1 concurrent story per user, the work is idempotent against the Firestore doc (Phase 2), and a queue's natural retry behavior (run-the-handler-again) is exactly what our resume protocol does on the next request. Cloud Tasks becomes the right answer if we hit ≥ 10 concurrent jobs or need cross-region failover. Not today.
3. **Cloud Functions has the same 540 s ceiling as Cloud Run's default and a worse cold-start story for image-heavy workloads.** No upside; rewriting our pipeline into a function harness is real cost.
4. **A separate Cloud Run worker service** is the right step *after* we have evidence that a single service can't handle both the API and the long-running work (Phase 1 might surface that — e.g., if memory profiles show the worker stages compete with concurrent API calls on the same instance). Premature today.

**Idempotency / resume trigger.** If the worker crashes mid-job, the next `POST /api/stories/generate` would be from a *new* user action — that does not resume an old job. Resume must be triggered separately:

- Add `POST /api/stories/:id/resume` (auth-required, owner-only). Reads the Firestore doc; if `status === 'generating'` and `workerHeartbeatAt` is stale (> 90 s) OR `status === 'failed'` with a resumable `failureReason`, it re-fires the background task against the existing doc. Returns `{ jobId, storyId }` like the create endpoint.
- The mobile library screen exposes a "Resume" affordance on rows whose `status === 'generating'` with stale heartbeat or `status === 'failed-resumable'`.
- The orphan sweep (Phase 4) does not auto-resume — it marks stale jobs as `failed` so the UI can surface the resume button. Auto-resume risks unbounded retry loops on a genuinely-broken job.

**Auth on the background task.** The Firebase ID token verified by `authMiddleware` is only valid for the initial HTTP request (1 hr by default, but we shouldn't rely on it). The background worker writes to Firestore using the backend's service-account credentials, not the user's token — same as today. No auth issue.

### Phase 4 — UX wiring, silent-success fix, and orphan sweep

1. **Fix the silent-success bug first (can ship the moment Phase 2's Firestore progress writes are live, before Phase 3's async refactor).** This is the single highest-impact user fix in this whole plan.
   - **Mobile** (`mobile/services/api.ts` + `mobile/app/(tabs)/create.tsx`): drop the 600 s axios timeout on `generateStory` to ~30 s. Subscribe to the story doc via `onSnapshot` (using the existing `firebase/firestore` package — already a transitive dep) the moment the POST is dispatched, *not* when it returns. Even pre-Phase-3, when the POST is still synchronous, the client can stop waiting on the HTTP response and instead watch the doc for `status === 'complete'`. The HTTP response becomes confirmation, not data.
   - This single change eliminates the "user sees error, story appears anyway" bug. The story doc is the source of truth; the HTTP response is a hint.
   - Tradeoff: pre-Phase-3, the backend is still synchronously running for 3–5 min and a hard error path (5xx) won't reach the mobile client because we already stopped listening. Mitigation: the orphan sweep (below) marks failed jobs `status: 'failed'` in Firestore, and the `onSnapshot` subscription sees that. Same observable behavior; durable via Firestore.

2. **Live progress UI** (`mobile/app/(tabs)/create.tsx` or a new `mobile/app/story/[id]/generating.tsx` screen). Subscribe to the doc; render `progress.message` and a determinate bar from `progress.completedSteps / progress.totalSteps`. On `status === 'complete'`, navigate to the reader. On `status === 'failed'`, show error + a Resume button (Phase 3's `POST /resume`).

3. **"We'll notify you when done" wording on the create screen.** Once the POST returns `{ jobId, storyId }` (Phase 3) or the `onSnapshot` is live (Phase 2 silent-success fix), let the user navigate away from the create screen. The story shows up in the library with a `status === 'generating'` row, progress message inline, animated indicator. No push notification this round — passive in-app surface is enough; an actual push notification is a follow-up (out of scope).

4. **Library handles all three statuses** (`mobile/app/(tabs)/index.tsx`). Today the `getStories` query filters `status === 'complete'` (see `backend/src/routes/stories.ts:219`). Loosen to return `generating | complete | failed` for the owner; the UI renders each appropriately. Doing this server-side keeps the contract clean.

5. **Orphan sweep.** A scheduled Cloud Scheduler → HTTP endpoint (`POST /api/stories/sweep-orphans`, service-account-auth only) that runs every 5 minutes and marks any story doc with `status === 'generating'` AND `workerHeartbeatAt` older than 5 minutes as `status: 'failed', failureReason: 'orphaned'`. Implementation: small endpoint in `backend/src/routes/stories.ts` (or a new `backend/src/routes/admin.ts` to keep auth separate). Setup is one `gcloud scheduler jobs create http` invocation — documented in the rollout. Without this, a zombie row sits in the library forever after an instance death.

6. **Broaden `isRetryableError` retry budget for `fetch failed` / network reset errors.** FC-020's review fix tightened the predicate (good), but the 2026-05-12 death was triggered by `TypeError: fetch failed sending request` on a char-ref call, which is a connection-level error, not a status code. Confirm via Phase 1's call-wrapper logging that this class is *retryable*, then add an explicit ECONNRESET / `fetch failed` arm to `isRetryableError` in `backend/src/services/textVerify.ts`. Keep the existing 5xx + jittered-backoff machinery; this is a one-line addition.

- `mapWithConcurrency` from `backend/src/services/textVerify.ts` — already wraps the parallel page batch; extend with an `onItemComplete(result)` callback to fire per-page Firestore writes.

- The `firebase` v11 SDK on mobile — already a dep for Auth; just add a Firestore `onSnapshot` subscription. No new packages.

## Risks & mitigations

- **Phase 1 finds nothing conclusive.** *Mitigation:* if a 12-page stress run and three production runs don't reproduce the death and don't show a clear memory or call-failure pattern, default the architecture to the most defensive interpretation (assume OOM): bound concurrent char-ref bytes resident in memory by streaming/discarding base64 once a ref's URL is persisted (re-download on demand for downstream prompts). Do *not* skip the per-ref persistence step — it's correct regardless of the death's actual cause.
- **Resume protocol corrupts a story if two workers hold the same job.** *Mitigation:* the `workerId` field is checked-and-set with a Firestore transaction at the start of every job/resume: a worker only proceeds if it can claim the slot (existing `workerId` is empty or its heartbeat is stale > 90 s). Conflicts → return 409 from `/resume`; the UI tells the user "already in progress." Single-writer invariant preserved.
- **Cloud Run CPU throttling kills the background task between responses.** *Mitigation:* explicitly verify and (if needed) flip the service to **CPU always allocated**. This is the single Cloud Run config knob that makes the background-task pattern work; check it as the first step of Phase 3, not after deploy. If the team prefers not to pay for always-on CPU, the fallback is a separate Cloud Run worker service triggered via Cloud Tasks (not this plan's recommendation, but the contingency).
- **`onSnapshot` cost / quota.** Firestore charges per document read for `onSnapshot` updates. One story generation produces ~20–30 progress writes → ~20–30 reads per subscribed client. At any plausible volume (< 10 concurrent jobs), cost is negligible (~$0 within free tier). Document in the FC; revisit if user growth makes it material.
- **Background task error surfacing is harder than HTTP error surfacing.** A failure in the background path can't `res.status(500)` — it has to set `status: 'failed'` on the doc. *Mitigation:* wrap the background entrypoint in a top-level try/catch that always writes terminal state (success or failure); add a Cloud Run log-based alert on uncaught exceptions in the generation path so we get notified out-of-band as well.
- **Resume edge case: page-1 (canonical anchor) was generated but its bytes weren't persisted as a separately-fetchable artifact.** *Mitigation:* the public URL → `bucket.file(path).download()` round-trip works for any uploaded image; there's no separate "anchor bytes" persistence to design. Confirm during implementation that all anchor pages are uploaded to a stable, derivable path (they are — `stories/{id}/page-N`).
- **Silent-success fix shipped pre-Phase-3 means the backend is still doing 3–5 min sync work but the client has already stopped listening.** *Mitigation:* this is *strictly better* than today's behavior (Firestore-driven completion + orphan-sweep covers failure). It is *not* worse on any axis. The full Phase 3 refactor closes the remaining residual (the backend keeps a useless `req`/`res` open for 3–5 min).
- **Mobile Firestore SDK adds bundle size.** ~80 KB gzipped for `firebase/firestore`. Acceptable; we're already shipping Auth from the same package.

## Rollout

- **Order of deploy (each its own PR; each independently safe to revert):**
  1. **Phase 1 prep PR.** Instrumentation only — per-phase memory/timing logs, request-scoped log tag, Gemini call wrapper. No behavior change. Deploy; run the 12-page stress test + capture ≥ 3 production runs; write the investigation note. Gate Phase 2 on a named root cause.
  2. **Phase 2 PR.** Resume-aware `generateAllIllustrations`, per-phase Firestore writes, worker heartbeat, extended `StoryDocument` type, `isRetryableError` widening for `fetch failed`. No mobile changes; HTTP contract unchanged. Deploy; verify a fresh story generates end-to-end with all per-phase writes landing.
  3. **Silent-success fix PR.** Mobile-only: lower axios timeout, switch create flow to `onSnapshot`-driven completion. Backend unchanged. This is the user-visible win and can ship the day Phase 2 lands.
  4. **Phase 3 PR.** Backend: convert `POST /generate` to 202 ACK + fire-and-forget; add `/resume`; verify CPU-always-allocated; add orphan-sweep endpoint + Cloud Scheduler job. Mobile: library renders `generating`/`failed` rows; Resume button wired. Single PR (the backend contract change + mobile rendering change ship together — clean rollback boundary).
- **Feature flag:** in Phase 3 backend, gate the 202-ACK path behind `ASYNC_JOBS_ENABLED=true` env var for the first 24h after deploy. With it off, the endpoint awaits like today (still benefits from Phase 2's progress writes). Flip on after a clean canary story. Remove the flag in a follow-up cleanup PR.
- **Monitoring after each deploy:**
  - Phase 1: memory traces present in logs; call-failure wrapper firing on every Gemini call.
  - Phase 2: every new story doc has a populated `progress` field updating ≥ 5 times during generation; `workerHeartbeatAt` is non-stale during a run.
  - Silent-success: zero mobile "Generation failed" toasts on runs where Firestore eventually marks `status: complete`.
  - Phase 3: 202 ACK p50 < 500 ms; background tasks reaching `status: complete` at the same rate as today's sync runs; orphan sweep firing every 5 min with 0 false positives in the first week.
- **Rollback plan (per phase):** revert the PR. Phases 1 and 2 are zero-behavior-change for the client and revert cleanly. Silent-success fix reverts to the 600 s timeout + sync-await flow. Phase 3 reverts to the synchronous endpoint (Phase 2's progress writes keep working — they're not coupled to Phase 3). Each PR is its own rollback unit.
