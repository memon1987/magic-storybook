## Context

The audience is children; the input authors are parents. Today the **only** safety mechanism is reactive: `sanitizeFailureReason` in [`backend/src/services/worker.ts`](../../backend/src/services/worker.ts) (line 108) maps Gemini's own safety refusals (`/safety|blocked|policy/`) to the `safety_blocked` failure code, which mobile's `generating.tsx` already renders with resume suppressed. Everything upstream is wide open:

- **Free-text inputs flow straight into prompts.** [`mobile/app/(tabs)/create.tsx`](../../mobile/app/(tabs)/create.tsx) collects `childName`, `favoriteAnimal`, `setting`, and `moral` as free text (steps 0-3); the API additionally accepts free-text `specialFriendName`, `specialFriendDescription`, and legacy `authorStyle` ([`routes/stories.ts`](../../backend/src/routes/stories.ts) lines 170-216 validate only presence + enums for length/artStyle/writingStyle). All of them are interpolated verbatim into `buildStoryPrompt` ([`prompts/story.ts`](../../backend/src/prompts/story.ts) lines 122-153).
- **No explicit `safetySettings` on any Gemini call.** All five `generateContent` sites in [`services/gemini.ts`](../../backend/src/services/gemini.ts) (story text ~L139, page image ~L410, char ref ~L527, cast ref ~L610, title page ~L695) pass config with only `responseModalities` — we rely entirely on model defaults.
- **No output moderation** between story-text generation and illustration/persist.
- **PII in logs:** `childName` itself is never logged directly, but the story prompt forces the child to be the FIRST `characterSheets` entry (story.ts L153) — so the child's real name reaches backend logs and structured telemetry as `character.name`: gemini.ts console logs at lines 516, 535, 564, 568, 573, 602, 836, 852, 873, 910; `emitStageEvent` `detail: { name: character.name }` at lines 557 and 577; and the placeholder URL at line 581 embeds the name.

**SDK verification (done during planning):** installed `@google/genai` is **0.7.0** (`backend/node_modules/@google/genai`, matches `^0.7.0` in package.json). Its `GenerateContentConfig` exposes `safetySettings?: SafetySetting[]`, with `HarmCategory` (`HARM_CATEGORY_HARASSMENT`, `HARM_CATEGORY_HATE_SPEECH`, `HARM_CATEGORY_SEXUALLY_EXPLICIT`, `HARM_CATEGORY_DANGEROUS_CONTENT`, `HARM_CATEGORY_CIVIC_INTEGRITY`) and `HarmBlockThreshold` (`BLOCK_LOW_AND_ABOVE`, `BLOCK_MEDIUM_AND_ABOVE`, `BLOCK_ONLY_HIGH`, `BLOCK_NONE`, `OFF`) enums exported. The image calls use the **same** `GenerateContentConfig`, so `safetySettings` is type-legal on both text and image `generateContent` — this plan applies it to all five call sites. (Whether the image *endpoint* honors the field at runtime is verified in Rollout monitoring; a runtime `INVALID_ARGUMENT` on image calls would be caught by the existing per-call catch → treated per Risks below.)

## Goals

- No unsafe parent input reaches a Gemini prompt: server-side validation rejects it with a friendly 400 before the story doc is even created.
- Every Gemini call runs with explicit, strict `safetySettings` — never model defaults.
- No generated story text is illustrated or persisted without passing a moderation gate; violations route through the existing `safety_blocked` UX.
- `childName` (and character names, which include it) no longer appear in backend logs or `stage_event` telemetry. Prompts and Firestore user-owned docs are unaffected.
- Fail-closed everywhere: a classifier error/timeout/malformed response blocks, never allows.

## Non-goals

- **Image vision moderation** (OCR/vision check on generated illustrations) — deferred; file a follow-up FC candidate ("FC-0XX: vision moderation pass on generated pages") in `docs/FUTURE_CONSIDERATIONS.md` as part of this PR's bookkeeping.
- Changing the `safety_blocked` mobile copy or resume-suppression behavior (already correct in `generating.tsx`).
- COPPA-scoped audit of `childName` **storage** (Firestore docs, GCS filenames) — logs only here; storage review is a separate FC candidate.
- Changing `sanitizeFailureReason`'s regex or the `FailureCode` enum.
- Any change to the OCR text-verify pipeline.

## Proposed approach

One PR, four layers. All decisions below are final — do not re-litigate during execution.

### 1. Input layer — new `backend/src/services/inputSafety.ts`

- **Dependency:** add `obscenity` (pure JS profanity matcher, no API calls, actively maintained; pin `^0.4.3`) to `backend/package.json`. Use `RegExpMatcher` with `englishDataset` + `englishRecommendedTransformers` (catches leetspeak/spacing variants).
- **Custom term list:** a small curated array (`CUSTOM_UNSAFE_TERMS`) in `inputSafety.ts` for kid-app-specific unsafe terms obscenity's dataset misses (weapons, drugs, self-harm, adult themes — executor seeds ~20-40 lowercase terms, matched case-insensitively on word boundaries).
- **Rules per field** (validate whichever fields are present on the request):
  - `childName` ≤ 30 chars, `specialFriendName` ≤ 30, `favoriteAnimal` ≤ 40, `moral` ≤ 40, `setting` ≤ 60, `authorStyle` ≤ 60, `specialFriendDescription` ≤ 120.
  - Character allowlist for ALL of the above: Unicode letters, marks, spaces, hyphen, apostrophe (`/^[\p{L}\p{M}\s'’-]+$/u`) — rejects digits, emoji, symbols, and prompt-injection punctuation (`{}`, quotes, backticks). `specialFriendDescription` additionally allows `,` and `.`.
  - Profanity/unsafe-term screen (obscenity + custom list) on every field.
- **Export:** `validateStoryInputSafety(body: Record<string, unknown>): { ok: true } | { ok: false; field: string; reason: 'too_long' | 'invalid_chars' | 'unsafe_term' }`. First failure wins; never echo the offending value back in the reason.
- **Wire-up:** in `routes/stories.ts` `POST /generate`, after the existing writingStyle check (~line 216) and **before** `const storyId = uuid()` / `storyRef.set(...)` — reject with `400 { error: "Let's keep it kid-friendly! Please adjust the highlighted field.", code: 'input_rejected', field }`. No Firestore doc is created for rejected input.

### 2. Generation layer — explicit `safetySettings` in `gemini.ts`

- Import `HarmCategory, HarmBlockThreshold, SafetySetting` from `@google/genai`. Define one module-level constant:
  ```ts
  const SAFETY_SETTINGS: SafetySetting[] = [
    { category: HarmCategory.HARM_CATEGORY_HARASSMENT, threshold: HarmBlockThreshold.BLOCK_LOW_AND_ABOVE },
    { category: HarmCategory.HARM_CATEGORY_HATE_SPEECH, threshold: HarmBlockThreshold.BLOCK_LOW_AND_ABOVE },
    { category: HarmCategory.HARM_CATEGORY_SEXUALLY_EXPLICIT, threshold: HarmBlockThreshold.BLOCK_LOW_AND_ABOVE },
    { category: HarmCategory.HARM_CATEGORY_DANGEROUS_CONTENT, threshold: HarmBlockThreshold.BLOCK_LOW_AND_ABOVE },
  ];
  ```
  (`CIVIC_INTEGRITY` deliberately omitted — irrelevant to kids' stories, and adds false-positive surface.)
- Add `safetySettings: SAFETY_SETTINGS` to the `config` of all five `generateContent` sites listed in Context (story text gets a `config` object added; the four image sites extend their existing `config`). Also used by the moderation call in layer 3.
- A safety block surfaces as a thrown/failed response containing safety language → already maps to `safety_blocked` via `sanitizeFailureReason`. If the response instead comes back with empty candidates + `promptFeedback.blockReason`, the existing "No image data" / JSON-parse failure paths throw; executor should include `blockReason` in the thrown message (`... safety blocked: ${blockReason}`) where trivially accessible so the mapping hits `safety_blocked`, not `generation_error`.

### 3. Output layer — new `backend/src/services/moderation.ts`

- `export async function moderateStoryText(story: GeneratedStory, generate: (prompt: string) => Promise<string>): Promise<void>` — injectable `generate` so tests mock the model; production passes a thin wrapper around `ai.models.generateContent({ model: TEXT_MODEL, contents, config: { safetySettings } })` (TEXT_MODEL + client imported/shared from `gemini.ts` — export the `ai` client or a `generateText` helper, executor's choice, keep it minimal).
- Classifier prompt: strict, structured — "You are a content-safety classifier for a children's (ages 3-8) storybook app. Classify the FULL story text below. Respond ONLY with JSON: {\"verdict\": \"safe\"|\"unsafe\", \"category\": string, \"reason\": string}. Treat violence, weapons, adult themes, drugs, self-harm, hate, scary-beyond-mild-peril content as unsafe." Input = title + all `pages[].text` + `titlePage.text` concatenated.
- **Fail-closed:** wrap in a 30s timeout (`Promise.race`); on timeout, model error, or JSON that doesn't parse to `verdict: 'safe'`, throw `new ModerationBlockedError(...)` whose `message` contains the literal words `safety blocked` (plus category, never the story text) so `sanitizeFailureReason` maps it to `safety_blocked`. Only an explicit `verdict === 'safe'` passes.
- **Wire-up:** in `worker.ts` Phase 1, immediately after `story = await generateStory(input, storyId)` (~line 363) and **before** `writer.saveStoryText(story)`. Consequence: any persisted `storyText` has passed the gate, so the resume path (`state.storyText` present → phase skipped) correctly never re-moderates. Cost: one extra flash-text call per story (~1-3s, well under a cent).

### 4. PII — redact names from logs/telemetry

- `emitStageEvent` sites gemini.ts L557 + L577: replace `detail: { name: character.name }` with `detail: { charIndex, nameLength: character.name.length }` (charIndex = position in the generation batch).
- Console log sites gemini.ts L516, 535, 564, 568, 573, 602, 836, 852, 873, 910: replace interpolated names with `char#<idx>` / counts (e.g., "generating 3 character reference image(s)" without the name list).
- L581 placeholder URL: `placehold.co/...?text=${encodeURIComponent(character.name)}` → static `text=Character` (URL is filtered out before persistence anyway — this closes the external-request leak).
- **Keep:** names in prompts (required), Firestore doc fields + `progress.message` via `progressMessage(... { charName })` (user-owned, user-facing), and `characterReferenceUrls` keys (user-owned doc). Document every changed site in the PR description.
- Check `tools/diagnostics/` telemetry dashboard generator for consumers of `detail.name`; if it keys on it, update to `charIndex` in the same PR.

### 5. Mobile mirror — `create.tsx` (UX only; server is the enforcement point)

- Client-side caps + charset regex (same constants as §1 for `childName`/`favoriteAnimal`/`setting`/`moral`; duplicate the regex + caps locally — no shared package) checked in `canContinue` / on change; when violated, show inline copy under the input: "Let's keep it kid-friendly! Letters, spaces, hyphens and apostrophes only." Add `maxLength` on the `TextInput`s. No obscenity lib on the client (bundle weight, trivially bypassable — server catches it).
- `mutation.onError`: `services/api.ts` has no response interceptor, so a 400 currently surfaces as axios's generic "Request failed with status code 400". Extract `error.response?.data` (axios `isAxiosError`); when `code === 'input_rejected'`, show the friendly server `error` string in the Alert instead.

## Risks & mitigations

- **False positives on real names (Scunthorpe problem).** obscenity matches on word boundaries with transformers, but names are adversarial input for any matcher. Mitigation: required test cases for "O'Brien", "Mary-Jane", international names (e.g., "Åsa", "José" — the `\p{L}` allowlist admits them); keep `CUSTOM_UNSAFE_TERMS` small and whole-word.
- **`BLOCK_LOW_AND_ABOVE` over-blocks legitimate stories** (courage/bravery stories contain mild peril; DANGEROUS_CONTENT at LOW is the likeliest tripwire). Mitigation: rollout monitoring of `safety_blocked` rate (below); the documented fallback — pre-approved, no new plan needed — is relaxing **only** `HARM_CATEGORY_DANGEROUS_CONTENT` to `BLOCK_MEDIUM_AND_ABOVE`.
- **Image endpoint rejects `safetySettings` at runtime** (type-legal in SDK 0.7.0 but server behavior for `gemini-3.1-flash-image-preview` unverified). An `INVALID_ARGUMENT` would fail all image calls → placeholder pages. Mitigation: the manual checklist's "normal story generates end-to-end" catches this pre-merge on a real deploy; if it fires, scope `safetySettings` to text calls only and record the deviation in the plan's Execution notes + PR.
- **Moderation gate adds a failure mode to every story** (extra model call). Mitigation: fail-closed is the *decided* behavior; the 30s timeout bounds latency; `safety_blocked` suppresses retry loops on mobile (FC-031 budget also caps resume cost).
- **Telemetry consumers of `detail.name` break.** Mitigation: §4 explicitly checks `tools/diagnostics/`.

## Rollout

- Backend: normal Cloud Run deploy after merge (owner-run, not autonomous). No schema/migration; rejected inputs never create docs, so no data cleanup.
- Mobile: client validation + error copy ship in the next EAS build (no OTA). Old clients degrade gracefully — server 400 shows a generic axios message until the build ships; enforcement is unaffected.
- Monitoring: watch `safety_blocked` and `input_rejected` rates in Cloud Run logs for the first week (`gcloud run services logs read storybook-api --region us-central1 | grep -E "input_rejected|safety_blocked"`). Spike in `safety_blocked` on innocuous inputs → apply the pre-approved DANGEROUS_CONTENT threshold relaxation.
- Rollback: single revert of the PR; no persisted-state coupling.
